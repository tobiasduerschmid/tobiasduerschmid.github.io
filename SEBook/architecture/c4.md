Ask five developers to sketch the same system and you get five pictures, each with its own meaning for "service", "component", and an unlabeled arrow. The **C4 model** gives a team one small vocabulary for software structure (people, software systems, containers, components, and code) and a set of views that zoom from the whole system down to its code {% cite Brown2022C4 BrownC4Model %}. This chapter teaches that vocabulary together with **Responsibility-Driven Design** (RDD): at every zoom level, each element states what it must know, do, or decide, and names the collaborators it asks for help.

**Prerequisites:** the [software architecture chapter](/SEBook/software_architecture.html) and a reading knowledge of UML [class](/SEBook/uml_class_diagram.html) and [sequence](/SEBook/uml_sequence_diagram.html) diagrams. The [UML overview](/SEBook/uml.html) names deployment diagrams; the chapter explains the deployment notation it uses where it appears. Recommended background for [Interface Descriptions](#interface-descriptions): the [interoperability chapter](/SEBook/quality_attributes/interoperability.html). No knowledge of RDD is assumed.

After this chapter, you should be able to:

1. Distinguish person, software system, container, component, and code, and classify real artifacts, such as a single-page application, a database schema, a library, or a serverless function, at the right level.
2. Write KNOW, DO, and DECIDE responsibilities with one owner for each KNOW and DECIDE, and refine them from one level to the next.
3. Write relationships as sentences that give direction, intent, and, where it matters, technology.
4. Choose the views and levels a named audience needs for its question, and justify the levels you leave out.
5. Critique a view against the C4 review checklist and RDD heuristics, and repair it.
6. Explain what automated consistency checks can and cannot establish.
7. Write an interface description for a collaboration that crosses a container or system boundary: its syntax (operations, inputs, outputs, and typed fields) and its semantics (purpose, side effects, restrictions, errors, and each field's meaning, unit, or format); link each operation to the responsibilities it realizes and each relationship to the operation it uses; explain why agreeing on syntax alone does not make two systems interoperable; and tell a compatible interface change from one that needs a new version.

**Practice alongside:** the tutorial [The C4 Model in Practice](/SEBook/architecture/c4-tutorial) (about 90 minutes) works through objectives 1–6 in the editor, and the follow-up tutorial [Describe an interface](/SEBook/architecture/c4-interfaces-tutorial) (about 30 minutes) practices objective 7.

## A Shared Vocabulary

The four C's are the four zoom levels of a system's static structure: its **context**, its **containers**, the **components** inside a container, and the **code** inside a component. They work like maps of one territory at different scales {% cite Brown2022C4 %}. The C4 model fixes what the boxes *mean*, not how you draw them, and it is not a design method: you still design, and C4 makes the design discussable {% cite BrownC4Model %}.

## Diagrams Are Views of One Model

None of the course-registration figures in this chapter was drawn by hand. Each is computed from one text file, `design.yml`, that lists the people, systems, containers, and components with their responsibilities and relationships. Such a file is a **Design IR** (design intermediate representation): structured text that people, checking tools, and AI coding agents can all read, and of which every diagram is one view. Rename an element in the file, and every view that shows it changes. [Models, Not Pictures](#models-not-pictures) returns to what this makes possible.

# Abstractions

The C4 model names five kinds of element. Four nest inside one another; people stand outside and use what is inside.

**Person.** A human who uses a software system: a role such as Student, a persona, or a named individual. *Not to be confused with* a user account record, or with another system that calls yours.

**Software system.** The highest level of abstraction: software that delivers value to its users, human or not, usually built and owned by one team. Course Registration is one; so is the university's Billing System. *Not to be confused with* a department or a business domain. "External" means outside the system you are describing, not necessarily outside your organization: the Billing System belongs to the university but is built by another team.

**Container.** An application or a data store that must be running for the system to work: a server-side web application, a single-page application in the browser, a mobile app, a batch job, a serverless function, a database schema, a file store. Containers talk to each other across process or network boundaries. *Not to be confused with* a Docker container, which is only one way to package and run one; with the machine that hosts it; or with a library, such as a non-executable JAR, which runs inside a container (an executable JAR that runs on its own is a container).

**Component.** A group of related functionality behind a well-defined interface, inside one container. Components are not deployed on their own; their container is. The Registration API's Enrollment Policy is a component. *Not to be confused with* a package or folder, which may hold a component's code without being one. Other SEBook chapters use *component* for a separately deployable unit; in C4, that unit is a container.

**Code element.** A class, interface, function, enum, or module that implements a component, such as the `EnrollmentPolicy` class. *Not to be confused with* the component itself, which is usually several code elements. A module can realize a whole component or be one code element, depending on its size and interface.

A system contains containers, a container contains components, and code elements implement a component. Each level is a zoom step, not a mandatory diagram: draw the first two levels for every system and the last two only where they repay their upkeep {% cite Brown2022C4 %}. These definitions are adapted from the C4 model website; the license note is in the [attribution](#attribution) at the end of the chapter.

# Responsibilities

Boxes and arrows say what exists; responsibilities say why each box exists. **Responsibility-Driven Design** treats a design as a community of elements with obligations, collaborating to achieve what none can alone {% cite WirfsBrockWilkerson1989 WirfsBrock2003 %}. It grew up around objects, alongside Class, Responsibility, Collaborator (CRC) cards {% cite BeckCunningham1989 %}, but its questions work at every C4 level: what must this element know, do, or decide, and whom does it ask for help?

## Know, Do, Decide

A **responsibility** is an obligation of one of three kinds:

- **KNOW**: information the element can provide. *The Seat Gateway knows which seats are held for each enrollment attempt.*
- **DO**: work or an effect that the element carries out. *The Registration API holds a seat in every section of a plan, or in none.*
- **DECIDE**: a judgment that determines an outcome. *The Enrollment Policy decides whether prerequisites and unit caps allow an enrollment.*

A responsibility is a promise in plain language, not a piece of the implementation:

| Draft statement | Problem | Rewritten as a responsibility |
|---|---|---|
| `heldSeats` | Names a field | KNOW which seats are held for each enrollment attempt |
| `charge()`, "click Pay" | Names a method or a UI step | DO request tuition charges for a completed enrollment |
| "Manage enrollment" | Too vague to check | DECIDE whether a student may enroll in a section |
| "The coordinator checks prerequisites" | Picks an owner before the obligation is clear | DECIDE whether prerequisites allow enrollment, then choose its owner |

## Knows Does Not Mean Stores

KNOW means the element can *provide* the information: it may hold it, derive it, or obtain it from a collaborator. To report why an attempt was refused, the Registration Coordinator must know the reason, but it stores no eligibility rules; it asks the Enrollment Policy and passes the answer on.

**Ownership** is a stronger promise than knowing:

- The owner of a **fact** is its single source of truth and its only writer. The `owns` slot lists the facts an element alone writes. Other elements may also KNOW the fact, by asking its owner, without owning it. A container and the component inside it that writes the fact may both list it, because the component's ownership refines the container's; two owners outside one containment chain are a conflict.
- The owner of a **decision** is the one element that makes it. Others may learn the outcome, and its reason, by asking.
- A **DO** is carried by the element it is allocated to. Work may be shared among several elements, usually with one of them coordinating the others.

The Seat Gateway owns seat holds. The Registration Database *stores* them, but storage is a DO, custody rather than authority: the database holds no business decision of its own about seats.

The working rule: **one owner for each fact and each decision**, that is, for each KNOW and each DECIDE. If both the Seat Gateway and the Registration Coordinator wrote seat holds, the two write paths would disagree after the first partial failure, and nobody could say which record was right. The coordinator may still *know* which seats are held, as long as it asks the Seat Gateway.

## Collaborations Become Relationships

A **collaboration** is a request for help: one element asks another to fulfill one of its responsibilities. In a C4 view it becomes a relationship, an arrow from the element that asks to the element that helps, labeled with what is asked. Read each label aloud as a sentence: "Registration Coordinator *asks for an eligibility decision from* Enrollment Policy". Ending the label with a preposition (*from*, *to*, *through*, *using*) keeps the direction readable {% cite Brown2022C4 %}. Write each relationship once, on the element that asks. Add a technology where an arrow between containers, or between a container and another system, crosses a container boundary, because there the protocol becomes a design decision; arrows from people may omit it.

## Writing It Down

A `design.yml` file needs few keys. People and systems sit at the top level. Every software element has the same slots: `responsibilities`, `collaborators`, and `owns`, plus optional ones such as `invariants`, `quality`, and `choices`. Here is the minimal subset at the system level:

```yaml
name: Course Registration
people:
  student:
    name: Student
    description: Plans and confirms one term schedule.
    collaborators:
      registration: plans a schedule and enrolls using
systems:
  registration:
    name: Course Registration
    responsibilities:
      - know: which seats are held for each enrollment attempt
      - do: hold a seat in every section of a plan, or in none
      - decide: whether a student may enroll in a section
    collaborators:
      billing: requests tuition charges from
  billing:
    name: Billing System
    external: true
    description: Charges tuition and fees for the university.
```

One level down, the same slots repeat. A system lists its containers under `containers`, a container its components under `components`, and a component its classes under `code`. The next section shows the first two; [step 2 of the worked example](#step-2-assign-owners) builds containers from scratch.

**Coming from a design file that lists collaborators as noun phrases?** A line such as `CourseCatalog: section facts` says what flows, not who asks for what. Rewrite it as a verb phrase that reads in the direction of the arrow, `course-catalog: asks for section meeting times from`, on the element that asks. A CRC card names its collaborators, which tells you whom an element asks; the relationship label adds *what* it asks for.

## Refinement Across Levels

Zooming in divides the parent's obligations among the children and adds the coordination and supporting knowledge they need. A container's responsibility **refines** the system responsibility it helps realize, and a component's refines a container's. Give the parent an `id` and point to it with `refines`. In the chapter's model, one decision travels down three levels:

```yaml
systems:
  registration:
    responsibilities:
      - decide: whether a student may enroll in a section
        id: sys-eligibility
    containers:
      api:
        responsibilities:
          - decide: whether a student may enroll in a section
            id: api-eligibility
            refines: sys-eligibility
        components:
          policy:
            responsibilities:
              - decide: whether prerequisites and unit caps allow enrollment
                refines: api-eligibility
```

Refinement makes coverage checkable. Every parent responsibility must be refined somewhere below it, and a reviewer can follow any obligation down to the element that carries it out. A new child responsibility that refines nothing, such as a coordinator's "sequence one enrollment attempt", is fine when it exists to serve one of the parent's obligations; one that serves none is a sign of scope creep.

## Roles and Control Style

Six **role stereotypes** ask what an element is for {% cite WirfsBrock2003 %}:

- An *information holder* knows facts.
- A *structurer* maintains relationships among things.
- A *service provider* performs work.
- A *coordinator* reacts to events and delegates.
- A *controller* makes decisions and directs others.
- An *interfacer* translates across a boundary: to a user, to another system, or to another part of the same system, such as its database.

In the chapter's model, the Seat Gateway and Billing Gateway are interfacers, the Enrollment Policy is a service provider, and the Registration Coordinator is a coordinator. A stereotype is a prompt, not a rule; an interfacer that crosses no boundary deserves a second look.

**Control style** describes where decisions live {% cite WirfsBrock2003 %}. In a *centralized* style, one controller makes nearly every decision while its collaborators hold data. In a *delegated* style, a coordinator sequences the work and lets capable collaborators decide within their own areas. The Registration Coordinator is delegated: it decides only which step runs next. Delegation keeps each decision next to its knowledge but spreads control over more elements; [Trade-offs](#c4-trade-offs) shows who pays for that.

# Zooming In

Zooming turns requirements into a design someone can build: decide the system's obligations, allocate each one to an element, connect the elements, and repeat one level down. The worked example shows each step; the sections after it describe each level.

## Worked Example: Requirements to Components

The example starts from three requirements:

- **FR-07:** A student who lacks a prerequisite or would exceed the unit cap is refused before any seat is held, and is told why.
- **FR-09:** A student is enrolled in every section of a plan, or in none.
- **FR-11:** Every completed enrollment is charged tuition, and a billing outage never delays an enrollment.

Each step shows the YAML it adds and the view it produces. A figure's *Open in the C4 editor* link shows its complete YAML.

### Step 1: Identify responsibilities

Ask what each requirement obliges the system to know, do, or decide. **FR-07** asks for a judgment, whether prerequisites and the unit cap let the student enroll, with its reason: a DECIDE. (The reason is part of the decision's answer; the element that reports it can KNOW it by asking.) **FR-09** asks for an action with a guarantee: a DO. **FR-11** has two parts. Charging is the Billing System's job, so this system's obligation is to *request* the charge: a DO. "Never delays an enrollment" is a constraint, not an obligation; it will shape step 3.

```yaml
requirements:
  FR-07: A student who lacks a prerequisite or would exceed the unit cap is refused before any seat is held, and is told why.
  FR-09: A student is enrolled in every section of a plan, or in none.
  FR-11: Every completed enrollment is charged tuition, and a billing outage never delays an enrollment.
systems:
  registration:
    responsibilities:
      - decide: whether a student may enroll in a section
        id: sys-eligibility
        requirements: [FR-07]
      - do: hold a seat in every section of a plan, or in none
        id: sys-holds
        requirements: [FR-09]
      - do: request tuition charges for every completed enrollment
        id: sys-billing
        requirements: [FR-11]
```

The `id` lets lower levels refine a responsibility; the `requirements` list lets a reviewer trace it back. The KNOW about held seats from [Writing It Down](#writing-it-down) has left the system level: no requirement asks the system to report held seats, so that knowledge appears in step 4, on the component that needs it.

### Step 2: Assign owners

Choose the containers, then allocate each system responsibility to the container that realizes it, with `refines` pointing back up; each KNOW and each DECIDE goes to exactly one container. Here, the Planner Web App runs in the student's browser, the Registration API on university servers, and the Registration Database stores what the API writes. The eligibility decision goes to the API.

## Interface Descriptions

Interfaces are not another level: you describe one wherever a client crosses the boundary of a system, a container, or a component. Here an *interface* is the contract an element offers to clients outside it, not a programming-language interface type such as `EnrollmentRule` in the code view. A relationship such as "Planner Web App submits plans to Registration API *[JSON/HTTPS]*" says who asks whom, and why; the interface description says how to ask and how to read the answer. Two independently built systems are *syntactically* interoperable when each can parse and validate what the other sends, and *semantically* interoperable only when both read the exchanged data the same way; the [interoperability chapter](/SEBook/quality_attributes/interoperability.html#syntactic-vs-semantic-interoperability) defines both and covers adapters, trade-offs, and practical interoperability. This section shows how to write such a description in a C4 model, and how to read it.

The Registration API offers one interface, the Enrollment API, to the Planner Web App. Here is its **syntactic view**: what a client sends and receives, and the type of every field.

<details markdown="1">
<summary>Show what the syntactic view leaves open</summary>

Among the readings this view allows: `units_enrolled` could count courses, quarter units, or semester units, and could be the term's total or only what this attempt added. `decided_at` has no time zone. `term` could be written "Winter 2027" or "2027-winter". Nothing says whether a refused plan leaves seats from an earlier attempt, who may call the operation, or what the client should do when a call fails.

Misreadings like these lost a spacecraft. The interface specification for a file of thruster data required newton-seconds; the ground software that wrote the file used pound-force seconds, and the navigation software that read it took every value as newton-seconds. The file was well formed, and no test compared its values with the specification, so the Mars Climate Orbiter flew far closer to Mars than planned and was lost in 1999 {% cite MCOMIB1999 %}.

The same structure hides in this model. When an enrollment completes, the Billing Gateway tells the Billing System how much tuition to charge in a field `amount`. If the description said only `amount: integer`, the gateway could send 4184, meaning dollars, and Billing could read 4184 cents: every message would validate, and every student would be charged $41.84 instead of $4,184. So the description of that message states `unit: US cents`, and its meaning says that the amount excludes financial aid and fees.

</details>

The full description adds the **semantic view**. Compare your two answers with it.

{% include c4-view.html model="course-registration" view="interface enrollment-api" caption="Full interface description of the Enrollment API: the syntactic view, the semantic view, and data tables that keep each field's type in the same row as its meaning, unit, or format." %}

The **syntactic view** is everything a parser needs: the interface's style, technology, and version; each operation's syntax line as a client would write it (`POST /v1/enrollments`), with its input and output; and each type's fields with their types, whether they are required, their allowed values, and their constraints, such as "1 to 8 items, no duplicates". The **semantic view** says what all of it means:

- **Purpose** says when a client calls the operation and what the provider then does: decide eligibility, then enroll the student in every section of the plan, or in none.
- **Side effects** are the changes a client can observe afterwards, outside the provider: an enrolled outcome holds seats and requests a tuition charge, and a refused one changes nothing.
- **Usage restrictions** say who may call and under which conditions: only the Planner Web App, for the signed-in student, at most 10 requests a minute.
- **Errors** say what can go wrong, why, and what the client should do then. Errors that apply to every operation, such as a caller who is not signed in as the student (401), are written once for the whole interface.
- **Examples** pair one input with its output, often the quickest way for a developer to check a reading.
- **Each field's meaning, unit, and format**, and a meaning for each allowed value, say how to read the data: `units_enrolled` counts quarter units and is the term's total after this attempt, `decided_at` carries a UTC offset, and `refused` means the student holds no new seat.
- **The vocabulary** defines the terms both sides must read the same way. *Quarter unit* is shared by the whole model; *section* and *plan* belong to this interface.

The operation also names the responsibilities it **realizes**: deciding eligibility, holding every seat or none, and requesting the tuition charge, the Registration API's three obligations. An operation may also name a responsibility of one of the provider's components, but only one that refines a responsibility of the provider. A component's own obligation, such as the coordinator's "sequence one enrollment attempt", is how the provider divides its work, and it stays out of the contract. Read this way, an interface description is the responsibility-driven contract made explicit {% cite WirfsBrock2003 %}: the purpose and `realizes` advertise a responsibility, the input is the information the client supplies, the restrictions are the conditions of use, and the output, side effects, and errors are the aftereffects. What stays out is how the provider keeps its promises. No operation or field mentions the Enrollment Policy's rule objects or how the database stores seat holds, so the team can change both without breaking a client.

Three remedies close the gap between agreeing on syntax and agreeing on meaning. **Document the semantics**, as the semantic view does. **Agree on a shared vocabulary**, so that both teams read *quarter unit* and *section* the same way. And **test both implementations together**, for example by sending the documented example to the real API and comparing the response. A schema (JSON Schema, OpenAPI) checks the syntactic view automatically; only people and integration tests check the semantic view. A stated unit is what makes such a test possible: a test can compare a number with "US cents", but not with "the amount".

**Changing an interface.** Clients are built against the description, so changing it changes what every client relies on. A change is *compatible* when every existing client keeps working without changing: adding an optional field is compatible, because clients that do not send it, or do not read it, are unaffected. Removing or renaming a field, or making an optional field required, breaks clients that already send or read it, so it needs a new `version`, and every client must move to it. The Enrollment API's `version: 1` tells a client which description it was built against. [Decomposition Has Costs](#decomposition-has-costs) weighs what versions cost.

**Guidelines.** Describe how elements interact and what a client can observe, never how the provider works inside. Expose only what clients need to use the interface, so the implementation can change without them. Keep the description minimal and organized around what clients do, so that it stays readable {% cite Clements2010 %}.

# Notation

The C4 model prescribes no shapes or colors. It asks every diagram to explain itself, so that a reader needs neither the author nor a guess {% cite Brown2022C4 %}. The renderer on this site draws every view the same way, but these rules apply to any tool, and to a whiteboard.

## Anatomy of a View

{% include c4-view.html model="course-registration" view="context of registration" caption="System context view of Course Registration, with the parts every C4 view needs: a title, type text in every box, sentence labels on arrows, and a legend. This model also draws its optional enterprise boundary." %}

1. **Title:** the view type and its scope, so a printed page explains itself.
2. **Type text in every box,** such as *[Person]* or *[Software System]*, with "external" added where it applies. Shapes help at a glance, but the text carries the meaning; a cylinder means "database" only to someone who has been told.
3. **Color never alone:** the Billing System is gray *and* says "external", so a reader with a color-vision deficiency, or a grayscale printout, loses nothing.
4. **Relationship sentences:** "Student plans a schedule and enrolls using Course Registration". Context views omit technology; container and component views add it on a second line where an arrow between containers, or between a container and another system, crosses a container boundary.
5. **Boundaries:** in a container or component view, a dashed box marks what was opened. An enterprise boundary is optional. Here the dashed box labeled with the university's name (UCLA, the University of California, Los Angeles) contains every element, so it separates nothing; the [landscape](#system-landscape) below shows one that does.
6. **Legend:** only the shapes, colors, and line styles this view uses.

Four more conventions: each element keeps **one name** in every view; **one arrow direction** holds throughout (here, from the element that starts an interaction); boxes keep **equal sizes**, because, as Brown observes, readers assume a bigger box matters more; and **abbreviations** are spelled out or explained in the legend {% cite Brown2022C4 %}.

Interfaces stay off these views unless you ask for them. A view selector with the suffix `with interfaces`, such as `containers of registration with interfaces`, adds a line "Provides: Enrollment API" to each box that offers an [interface](#interface-descriptions), and a line "via Enrollment API" under the technology of each arrow that uses one.

## Review Checklist

Use this checklist before you share a view. It merges the [review checklist on the C4 model website](https://c4model.com/diagrams/checklist) {% cite BrownC4Model %} with the checklist in Luca Mezzalira's IcePanel guide, [*Communicating Architecture with the C4 Model*](https://icepanel.io/ebook/communicating-architecture-with-the-c4-model), reworded, and adds RDD checks. The license note for the adapted parts is in the [attribution](#attribution).

- **Scope:** Does the title name the view type and scope? Does a short description say whom the view is for and which question it answers? Does it open one scope at one level, with everything else recognizable as context?
- **Elements:** Does every box have a specific name, a type, and a statement of what it is responsible for, and do containers and components name their technology? Are abbreviations explained, and names identical across views?
- **Relationships:** Does every arrow's label read as a sentence from source to target and say what is asked or sent? Do arrows between containers, or between a container and another system, name their technology, and are asynchronous ones marked? In a view shown `with interfaces`, does each arrow that crosses a container or system boundary name, on its "via" line, the interface it uses?
- **Presentation:** Does a legend explain every shape, color, line style, border, and arrowhead, with no meaning carried by color alone? Do box sizes mean nothing the legend does not explain? Can the intended audience read the view without its author?
- **Responsibilities:** Is every responsibility a KNOW, DO, or DECIDE obligation, not a field, method, or screen? Does each KNOW and DECIDE have exactly one owner, and do data stores hold no business decisions of their own? Do coordinators sequence and delegate, with no element hoarding decisions or collaborators?

The four levels describe static structure. ## Deployment View

A deployment view maps container instances onto infrastructure in one named environment. # Models, Not Pictures

## One Model, Many Views

A **model** holds the elements, their nesting, responsibilities, and relationships; a **view** selects part of the model to answer one question for one audience; a **diagram** draws a view with a notation and a layout. Moving a box changes the layout, not the model. Renaming an element renames it in every view, where a drawing tool would send you hunting through every diagram. Leaving an element out of a view does not delete it. And some knowledge lives only in the model: requirement links, `refines` chains, owned facts, invariants, quality targets, and decisions.

## Derived Relationships

In [step 4 of the worked example](#step-4-zoom-in), the container view kept its arrows after the API's relationships moved down to its components. The view *derives* them by lifting each end of a relationship to the nearest element it shows: "Seat Gateway writes seat holds to Registration Database" appears as "Registration API writes seat holds to Registration Database" in the container view, and not at all in the context view, where both ends are inside Course Registration.

Three rules keep derived views honest. Relationships of the same kind (synchronous or asynchronous) that lift onto the same pair merge into one arrow, which shows the first description and how many more it stands for. A summary relationship written explicitly at the higher level wins over derived ones of the same kind. And a relationship attached to a system that no container sends or receives is drawn to the boundary in its own style, as in [step 2](#step-2-assign-owners), a visible reminder that an owner is missing. So declare each relationship once, at the most detailed level you know.

## What Checks Can and Cannot Establish

Because the model is structured text, a tool can check it. The editor on this site runs several dozen rules, which can establish some kinds of claim but not others:

| Kind of claim | Examples | Can a check establish it? |
|---|---|---|
| Consistency | Every collaborator exists; every `refines` points to an ancestor's responsibility; no deployment node hosts a component | Yes |
| Completeness and style | Every arrow has a description; arrows between containers name a technology; every container has a responsibility; no component has more than nine unrefined responsibilities | Yes, as rules with known exceptions |
| Likely smells | Names such as "Backend" or names ending in "Manager"; "handle registration"; one element that owns most of the decisions | Only as suggestions a person judges |
| Adequacy | The boundaries are right; eligibility belongs in the policy; enrollment finishes within 2 s; the code matches the model | No |

The three flawed models in [Zooming In](#zooming-in) show the gap. The checker **warns** about the "uses" arrows, which lack a meaningful description and a technology. It only **suggests** that "Backend" is a generic name and "handle registration" a vague responsibility, suggestions the editor's novice profile hides by default. And it says **nothing** about the database drawn as a software system. A team can legitimately own several software systems, so nothing in the model's structure shows that this one is really part of Course Registration; telling a part from a separate system is a boundary judgment for a reviewer. The flawed description card in [Interface Descriptions](#interface-descriptions) passes every check too: a check can see that a field states a unit, not whether the unit answers the client's question. A model that passes every check is consistent; whether it is a good design remains your judgment, and your reviewer's.

## Keeping Model and Code in Sync

A design that matched the code when it was written drifts as the code changes, and a stale design misleads its most trusting readers: newcomers, reviewers, and AI agents reading it as context. The [software architecture chapter](/SEBook/software_architecture.html#the-dichotomy-of-architecture) describes this drift between intended and actual architecture. Practices that keep a model honest:

- Keep `design.yml` in the repository, and change it in the same pull request as the code it describes.
- Make components visible in the code as modules named after them, and link elements to code with `source`: the architecturally evident coding style that Brown recommends, following George Fairbanks {% cite Brown2022C4 %}.
- Trace responsibilities to requirement ids, so a changed requirement points to the elements it affects.
- Generate views instead of redrawing them, run the checks in continuous integration, and ask an AI agent that changes code to update the model in the same change.

## Tools {#c4-tools}

Several tools treat C4 as a model rather than a drawing. **Structurizr**, built by Simon Brown, defines a model in a text DSL and renders its views. **IcePanel** is a visual modeling tool that keeps one model behind every diagram you draw. The **[C4 editor](/SEBook/tools/c4-editor)** on this site reads and writes `design.yml`, renders this chapter's views, and runs the checks. Drawing tools and whiteboards are the fastest way to explore, but they keep no model, so each picture drifts on its own.

## Recording Choices and Decisions

A model can also record *why*. The `choices` slot records technology and pattern choices on an element or relationship; `decisions` records architecture decisions and the elements they affect. The chapter's model records why billing uses a message queue, and why one database holds plans and seat holds:

```yaml
# On the Billing Gateway's relationship to the Billing System:
billing:
  description: requests tuition charges from
  technology: AMQP
  connector: message
  choices:
    technology: {chosen: RabbitMQ, alternatives: [synchronous HTTPS call], because: a billing outage must not block enrollment}

# At the top level of the model:
decisions:
  one-database:
    title: Keep plans and seat holds in one relational database
    status: accepted
    context: Seat holds and enrollment must commit atomically.
    decision: One PostgreSQL database with serializable transactions for seat holds.
    alternatives: [a separate seat service with its own store]
    consequences: The database is a single point of failure.
    affects: [db, seats]
```

A reviewer who disagrees with a choice can see which alternatives were weighed, and a checker can confirm that a recorded pattern has all its roles. Neither says the choice was right.

# Trade-offs {#c4-trade-offs}

## When C4 Helps and When It Hurts

In practitioners' experience, C4 helps most with **mixed audiences** (context views for product owners, container views for developers and operations), **onboarding**, **design review before implementation**, where discussion turns to named responsibilities instead of vague boxes, and **distributed systems**, whose container view *is* their shape {% cite Brown2022C4 %}. A structured model should also help **AI coding agents**, which can read the model instead of interpreting a picture and so should be left fewer decisions to guess.

It hurts when teams **draw every level for everything**, because component and code views of fast-changing code go stale and a stale view is worse than none; and when boxes carry **names and technologies but no responsibilities**, which look complete and explain nothing. It fits poorly when the hard part is **not static structure**, such as timing-critical embedded control (see [AADL](/SEBook/architecture/aadl)) or algorithms. For libraries, frameworks, and SDKs used by other developers, the C4 website itself suggests UML instead {% cite BrownC4Model %}.

## Which Levels to Draw

Every drawn view is a maintenance commitment, and the cost grows as you zoom in:

| View | Audience | How often it changes | Recommendation |
|---|---|---|---|
| System context | Everyone | Rarely | Draw it for every system |
| Container | Technical staff | Occasionally | Draw it for every system |
| Component | The container's developers | Often | Draw it for complex or risky containers; skip databases and simple services |
| Code | Developers | Constantly | Generate it on demand; draw it only for a key mechanism or pattern |

Leaving a level out is a decision you can justify. "The API's internals change weekly, so we generate its component view instead of maintaining a drawn one" is a reason; "we ran out of time" is not.

## What C4 Does Not Show

C4 describes static structure plus a few supporting views. It does not show whether a design meets its quality goals (latency, availability, security), how state changes over time, how data is modeled, where trust boundaries lie, or why a decision was made unless you record it. Other views answer those questions: state machines, data models, threat models, quality-attribute scenarios {% cite Bass2012 %}, and the broader view sets of Kruchten's 4+1 model {% cite Kruchten1995 %} and Views and Beyond {% cite Clements2010 %}. C4 orients the reader; it does not replace analysis.

## Decomposition Has Costs

Every new boundary adds an interface to maintain and a place where a request can fail. RDD's preferred delegated style has a cost too: decisions spread over several elements, so understanding a change means following collaborations. A controlled experiment measured this: 99 professional consultants and 59 students made the same changes to two Java designs, one delegated and one centralized {% cite ArisholmSjoberg2004 %}. Senior consultants changed the delegated design faster. Undergraduates and junior consultants struggled to understand it and did far better with the centralized one. The lesson is not that centralized control is better. Delegation pays off for maintainers who can follow it, so when maintainers are novices, keep delegation shallow. The study compared control styles, not documentation; still, a dynamic view that shows who asks whom, in what order, is one way to make delegation visible to newcomers.

Shared interfaces have a cost of their own. A change to an interface must be made in every system that uses it, so versions and extensible formats trade the effort of implementing an interface against the variability it allows {% cite Bass2012 %}: an optional field keeps existing clients working, while a change that needs a new version (see [Interface Descriptions](#interface-descriptions)) must reach every client before the old version can retire. An adapter can translate formats, units, and meanings, but only those both semantic views state. The interoperability chapter discusses both in its [trade-offs](/SEBook/quality_attributes/interoperability.html#trade-offs) and [practical interoperability](/SEBook/quality_attributes/interoperability.html#practical-interoperability) sections.

## UML or C4?

UML provides precise notations for many concerns: classes, interactions, states, deployment. C4 provides a small set of abstraction levels and says which question each level answers. They combine well: choose the C4 level that fits the question, then use UML where the view needs precise notation, as this site does for C4's code, dynamic, and deployment views.

## Diagrams as Code or a Modeling Tool?

Text models such as `design.yml` or the Structurizr DSL live in the repository, change through reviewed pull requests, and can be checked automatically and read by AI agents, at the price of less control over layout and a format some colleagues will not edit. Visual modeling tools invite the whole team in but keep the model outside the repository, often in a proprietary format. Drawing tools are fastest for a first sketch, and fastest to drift.

## What the Evidence Says

We know of no controlled study of whether C4 diagrams improve learning or design quality; the published reports are experience reports and course proposals, not comparisons. Treat C4 as a communication discipline, a shared vocabulary whose value comes from the questions it forces you to answer.

- **The Booking Ledger owns RB-02.** It is the only writer of bookings. ## Far Transfer: Air-Quality Alerts

<!-- objective: 4 -->
<!-- objective: 5 -->
<!-- objective: 6 -->
This brief has no starter model and no single answer. Work in the [C4 editor](/SEBook/tools/c4-editor) or on paper, then judge your work with the rubric after the tasks.

> **Brief.** A county health department wants residents to receive timely alerts about smoke and fine particles. A regional air-monitoring network, run by a separate agency, publishes a reading from each of its sensors every minute. A commercial text-message provider delivers alerts and charges per message.
>
> - **AQ-1:** A resident can subscribe to alerts for up to three neighborhoods, and can stop them by replying STOP.
> - **AQ-2:** When a neighborhood's one-hour average of fine-particle readings rises above its threshold, each of its subscribers receives one alert within 5 minutes, and at most one alert per neighborhood in any 6 hours.
> - **AQ-3:** The county health officer can change a neighborhood's threshold; readings that arrive after the change use the new threshold.
> - **AQ-4:** A sensor that sends no reading for 15 minutes is left out of averages, and the health officer can see which sensors are silent.

1. Write the context view: people, the focal system, the systems it depends on, and labeled relationships.
2. Write the system's KNOW, DO, and DECIDE responsibilities, each traced to a requirement.
3. Choose containers, allocate responsibilities with `refines`, and label every relationship. Which relationships are asynchronous, and why?
4. Zoom into the container that decides when to alert, and give each of its decisions one owner.
5. Choose views for two audiences: the county board approving the budget, and the engineer paged at 3 a.m. because alerts stopped. Which levels and supplementary views does each need, and which do you leave out?
6. Review the model with the checklist, then with the editor's checks. What did each find that the other missed?

**Rubric.** Rate your model on each criterion before you open the questions below:

- **Audience and levels:** each chosen view answers a stated question for a named reader, and each level you leave out has a reason.
- **One owner per KNOW and DECIDE:** every fact has one source of truth that alone writes it, and every decision has one element that makes it; others ask.
- **Labeled relationships:** every arrow reads as a sentence from source to target, names a technology where it crosses a container boundary, and marks asynchronous messages.
- **Refinement:** every system responsibility is refined below it, and every requirement traces to at least one responsibility.

<details markdown="1">
<summary>Show decisions to check</summary>

Check your design against these questions rather than a fixed answer:

- Which element owns the fact that a neighborhood was alerted in the last 6 hours, and is it the only writer? *Weak:* the alert decider and the message sender both record that an alert went out, so after a failed send the two records disagree. *Strong:* one element owns "last alert per neighborhood", and the sender reports each delivery to it instead of writing the record itself.
- Does the element that decides an alert store the readings, or ask the one that does? Either works, as long as the readings keep one owner: an alert decider that asks the reading store KNOWS the averages without owning them.
- Which element decides that a sensor is silent, and how does that decision reach the averages?
- How does a STOP reply reach the owner of subscriptions, and which way does that arrow point?
- Does AQ-2's 5-minute target hold when the text-message provider is slow? *Weak:* the alert decider calls the provider synchronously for each subscriber, so one slow response delays every alert behind it. *Strong:* the decider puts alerts on a queue and a separate sender delivers them, so the decision stays on time while sending catches up; the model records the queue as a choice and the 5-minute target as a quality statement.

</details>
