It is 2 July 2019. Imagine you are helping investigate a major outage. A visitor asks for a web page. For a site using Cloudflare, that request reaches Cloudflare before any needed work continues to the site's own server, called its origin. Cloudflare supplies services shared by many independent websites. We will follow only the request inspection path; caching and other features are outside this diagram.

The web application firewall, abbreviated web application firewall, examines requests for suspicious patterns. A rule describes something to recognize and what to do when it is recognized. The processor, or C P U, performs that work. Its capacity is finite: work spent inspecting one request is capacity unavailable for other work. The inspection step therefore has both a security responsibility and a progress obligation.

Now visitors to many sites see five oh two errors. That status says a gateway could not successfully complete its upstream work; it does not name the defective component. Cloudflare's first synthetic monitoring alert arrived at 13:45 U T C. A synthetic monitor sends test requests to observe the service. You have a symptom and a shared dependency, but you do not yet know whether demand increased, origins failed, or request processing became expensive. Which evidence should you seek first?

By 14:00, processor observations, system traces, and logs pointed to the web application firewall. Front-line servers accept traffic and delegate work to request-handling processes, called workers. The C P U serving web traffic was exhausted. A trace observes execution activity; a profile summarizes where time is spent. Either can narrow an investigation toward expensive work. Neither, by itself, explains why that work is excessive. The failure to visitors remains the five oh two response.

The team had just deployed a new rule intended to improve detection of cross-site scripting, an attack involving unwanted script execution in a web application. The change was merged at 13:31, built and tested at 13:37, and began rolling out at 13:42. Quicksilver distributed the configuration globally. Positive and negative matching tests passed. The rule was in simulate mode: matches would be logged rather than deliberately blocking requests. That is useful context, but what does it actually tell us about evaluation cost?

The request worker needs inspection to complete. Inspection invokes a regular-expression matcher: a program that checks text against a pattern. In this incident, excessive matching work consumed the C P U needed to serve requests. The front-line servers consequently produced five oh two errors. No intentional rule-based block is needed for that failure. This sequence explains the dependency; it is not a recovered trace of one particular visitor's request.

Availability is failing now. The web application firewall is implicated, and responders can terminate its operation globally. A narrower rollback would be desirable if it can be executed promptly, but the postmortem describes delays and obstructed access to recovery systems. The immediate objective is to stop the expensive work and restore request progress. Disabling a security function also has a cost that must be tracked. By 14:09, traffic and C P U had recovered. That supports the web application firewall containment decision, but it does not mean the web application firewall's security function is restored or identify every detail of the defective rule. Removing an entire component changes many things at once. We now need stronger evidence that the particular rule, under relevant inputs, explains the excessive work.

The public account does not publish the actual triggering requests, so we will not invent them.

The isolated checks supported the new rule as the cause. Its regular expression could make a backtracking matcher explore excessive alternatives. To understand that mechanism without source code, we will use a much smaller teaching task: decide whether a single-line text contains an equals sign. This is not the original security rule, and our example text is not a recovered incident request.

For this model, the functional obligation is to answer present if an equals sign exists, and absent otherwise. One candidate check asks whether an equals sign occurs at one proposed input position; revisiting a position counts again. We add a teaching budget: count the characters, add one, and multiply by four. For seven characters, at most thirty-two checks are allowed. This invented budget distinguishes a correct eventual answer from an acceptable execution.

Suppose the input has no equals sign. Evaluation stops because it reaches the work limit before finishing. We have not established the matching answer merely by stopping. Which result should the experiment record?

Our deliberately inefficient matcher starts at the beginning of the text. It lets a first skip consume any number of characters, then lets a second skip do the same, then requires an equals sign. If that requirement fails, it revises earlier choices. Trying alternative earlier choices is backtracking. Both skips can consume the same kinds of characters, so more than one allocation can lead to the same next position.

The input is three x characters, with no equals sign. First, the skips consume three and zero characters: the equals check fails at the end. Next, they consume two and one: the check fails at the same end. Next, they consume two and zero: the check fails before the last x. The diagram shows only three attempts. Each attempt is locally understandable, but some revisit a position that was already checked.

Hold the first skip at length one. On our three-character input, the second skip can then consume two, one, or zero characters. None produces an equals sign. Once those choices fail, the first skip can become zero and the second has four lengths to try. What does this suggest about shortening the input by one character?

For three characters, the four first-skip lengths leave one, two, three, and four choices for the second skip: ten candidate checks in total. More generally, each added character extends several possible allocations. Seven non-equals characters require thirty-six checks; thirty-two require five hundred sixty-one. These counts describe our fixed-start model. They do not measure Cloudflare's full expression, engine optimizations, or actual incident traffic.

We want a compact reproducer that still exceeds our teaching budget. At length seven, thirty-six candidate checks exceed the budget of thirty-two. At length six, twenty-eight checks equal the budget of twenty-eight, so the run completes within it. Deleting text until the matcher merely returns absent could erase the resource failure. We now have a causal mechanism: overlapping repetition allows a backtracking engine to explore many allocations; triggering inputs make that work expensive; inadequate protection lets the work interfere with serving requests. We also need incorrectness: which obligation is violated? A C P U being busy can be normal. Failure to make required request progress, or exceeding a specified work budget, supplies the missing requirement.

The full incident also involved missing barriers. A C P U safeguard had been removed during an earlier refactor, cost checks were absent from testing, and rule rollout bypassed ordinary staged deployment. Those conditions help explain why one expensive rule became a global outage. Which statement best captures a defensible diagnosis?

For our small task, a forward scan is enough. Inspect the next unexamined character. If it is equals, report present. Otherwise advance. At the end, report absent. No earlier position is revisited. That preserves the tiny task's intended answer while inspecting each character at most once. This is a teaching repair for finding equals, not a substitute for a security rule that must recognize more complex patterns.

Retain the original failing seven-character negative case and longer negative cases. Also challenge behavior on empty input and equals at the beginning, middle, and end. A matcher that always reports absent would be fast but wrong. A repair that merely raises the budget would leave the allocation growth unchanged. Return to the real service. Removing the offending rule addresses that deployed trigger. Performance tests challenge costly inputs before release. A matching engine with appropriate complexity guarantees changes what evaluation can cost. Runtime protection limits damage when work is still too expensive. Staged deployment exposes a smaller portion of traffic before expansion. A recovery path must remain usable when ordinary serving is impaired. These measures address different parts of the chain.
