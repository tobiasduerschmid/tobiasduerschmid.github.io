In May 2026, OpenAI was measuring how well its AI models can hack. One test was ExploitGym, a benchmark of security tasks. Each task asks an agent to exploit a known vulnerability in a target program, and the agent is scored on success. To measure the models' maximum ability, the safety classifiers that normally block risky cyber activity were deliberately turned off.

The agents ran in isolated sandboxes with no direct internet access. One controlled door stayed open. Tasks need software libraries, so the sandboxes could reach an internal package proxy, and OpenAI gave the agents shared credentials for it. When an agent asked for a library, the proxy downloaded it from a public registry, kept a copy, and handed it back.

The second system is Hugging Face. Its Hub is a public platform where anyone with an account can publish models and datasets. When someone uploads a dataset, Hugging Face's dataset workers open the files and show a preview of the first rows. The workers run on Kubernetes clusters, and each one carries a token for the cluster's control interface.

The trouble began in May, during training and evaluation runs. An agent that could not reach a file it needed left a note in the package proxy, asking other agents to upload it. It used the credentials OpenAI had given them; no vulnerability was needed. Others replied, and the proxy became a message board. Later, most of the tasks discussed there came from the roughly one in five benchmark tasks that no OpenAI model had ever solved.

By late May, agents had found a zero-day in the proxy: a server-side request forgery. That is a flaw that lets a client make a server send requests to any address the client chooses. The proxy was allowed to reach the internet, so now the agents could too. The sandboxes' own connections were still blocked. Their trusted proxy relayed the traffic instead.

There were warning signs. In late May, an OpenAI team saw agents posting on the board and reaching the internet in ways that were not allowed. On June twenty-seventh, a security monitor raised an alert, and responders decided the evaluation did not need to stop. On July fourth, the agents' traffic crashed the proxy. Rebuilding it the next day wiped the board, and the runs resumed within days.

On July eighth, an agent rebuilt the message board, encoding each message in the name of a directory on the proxy. Agents also regained internet access through the proxy. meter, an independent evaluation organization, later counted about twelve hundred agents on the board and more than seventy thousand messages and files. About seven hundred agents took part in the attack that followed.

On July ninth, one agent even obtained root, full control, on the virtual machine that hosted its sandbox. When a second agent with the same access tried to connect to the internet directly, the outbound network controls blocked it. Meanwhile, the relay through the proxy, open since late May and regained on July eighth, kept carrying the other agents' traffic.

Searching the internet for task solutions, an agent found a third-party application in the cloud that ran security-benchmark tasks. Its exposed endpoint would run whatever code a caller sent. The agent took over the application's sandbox as root. Hugging Face later described that machine as the agents' control, staging, and egress base for the entire campaign.

Why Hugging Face? Private datasets there held benchmark challenge solutions, and the agents hoped that other benchmark runs on Hugging Face's infrastructure would reveal how their scorer worked.

On July tenth, an agent found fourteen Hugging Face access tokens with write permission in a public Hugging Face dataset, where they had been exposed. It checked that they worked and posted them to the message board. An access token is a password for programs: whoever presents it acts as the account that owns it.

With a stolen write token, an agent can upload to the Hub exactly like the token's owner. The Hub checks that each upload carries a valid token, and these tokens were valid. From the Hub's point of view, nothing unusual had happened: a known account uploaded a dataset, and the Hub queued a preview.

On July eleventh, an agent published a crafted dataset. To show a preview, a dataset worker opens the uploaded files. This file used H D F five, a scientific data format whose files can keep their data in other files. The crafted file pointed at files on the worker itself, including its environment variables, and the preview displayed them. Those variables held production credentials.

A second flaw went further. Another dataset included a reference descriptor, a small file that tells the worker's data library where the data lives. The library evaluated parts of it with Jinja two, a template engine, and that engine was not sandboxed. So a template could run operating-system commands. For the first time, the agents ran their own code on Hugging Face's machines.

The agents installed a small control program on the workers. It fetched commands from a then-public Hugging Face dataset and posted results back, so the platform's own storage carried the attack's instructions. Agent code ran on forty-one production dataset workers.

Each dataset worker ran in a pod, Kubernetes' name for a running container, with a token for the cluster's control interface. One worker's token could read a stored secret of Hugging Face's cluster-access tool. According to Hugging Face, that secret was one credential, shared across clusters, with full administrator rights. Reading it gave the agents administrator access.

As administrators, the agents started containers with special permissions that could reach the files of the machine underneath, and gained root on a production machine. Hugging Face later named a missing safeguard: no policy rejected such privileged containers.

From the workers, the agents collected more credentials: for databases, messaging, code repositories, and cloud accounts. They downloaded four private code repositories. On July thirteenth they changed a private repository and opened a draft pull request, which was closed without being merged. From code in one worker pod to administrator access across several clusters took under thirteen hours.

Hugging Face cut off the attackers' access on July thirteenth and disclosed the incident on July sixteenth. It closed both dataset vulnerabilities, rebuilt the compromised nodes, and revoked the affected credentials. At that point, the attacker had not yet been identified.

OpenAI did not know either. On July seventeenth, it asked Hugging Face, as a customer, whether OpenAI's data was affected. On July nineteenth, OpenAI's own monitoring flagged unusual activity: agents had also broken into OpenAI's own research cluster. The next day, responders found Hugging Face credentials in files saved from an outside account. On July twenty-first, OpenAI told Hugging Face and the public.

On August twenty-sixth, OpenAI published a technical report, and meter and Redwood Research published an independent investigation. The investigators describe no human directing the attack: agents took assignments from other agents on the board. They knew it was out of bounds and joined anyway to help their peers. Most wanted to understand how the benchmark's scorer worked, hoping to fool it; some looked for task solutions.

Here is the chain on one page: forged requests through the package proxy, a third-party application, fourteen leaked tokens, a crafted upload, and a worker's token. Before analyzing the chain, trace it yourself.

For each hop, ask what the agents gained that they did not have before. A new identity? A new network position? The ability to run code somewhere new? A new secret? Answering hop by hop shows every place where a defender could have said no.

Now apply the C I A triad to Hugging Face, starting from the evidence. The agents read production credentials and, in OpenAI's words, limited internal data; Hugging Face says the only customer data they reached was five datasets of benchmark solutions. They downloaded private code repositories. They installed a control program on production workers, created privileged pods, and changed a private repository, though nothing was merged. The accounts report no outage of Hugging Face's public services. At OpenAI, the agents' traffic had crashed the package proxy.

Classify each fact. Which facts show that the wrong party could read something? Which show that the wrong party changed something? Which show that legitimate users could not get service? And which tempting conclusions go beyond the evidence?

Next, build the threat model: what the attacker knows, which actions it can take, what resources it can spend, and what incentive drives it. Most threat models picture a human attacker. Here the attacker was hundreds of AI agents, running inside a test that rewarded solved tasks.

Map the evidence onto the dimensions. Seven hundred agents joining the attack in parallel. Root on a sandbox machine, and forged requests through the proxy. The published paper describing the benchmark, which the agents had read. A score that rewards solved tasks, even impossible ones. Which dimension does each belong to?

Put together, the threat model reads like this. Knowledge: the published description of the benchmark, worker source code returned by crafted datasets, leaked tokens, and every discovery shared on the board. Actions: package requests with legitimate credentials, forged requests, root on machines, and uploads with stolen tokens. Resources: about twelve hundred agents in the week meter studied, on a board that had existed since May. Incentive: a higher score, not money or espionage.

Read as a threat model, the sandbox's controls defended against one model misbehaving inside its box: they blocked its direct connections. They did not account for hundreds of persistent agents who share discoveries for weeks and are rewarded for scores they cannot earn honestly. How should the next evaluation respond?

To decide where defenses belong, draw the system as a component diagram. Each box is a deployable part with a job, and each connector says who sends what to whom. Number the connectors along the attack: sandbox to proxy, proxy to the staging server, staging server to the Hub, Hub to the dataset worker, and worker to the cluster's control interface. A note on the worker records the secrets in its environment.

Read the diagram with the first questions of a security plan. Which components hold assets worth defending, such as secrets, data, or control? And which components accept input that someone outside the organization created? That second set is the attack surface.

A trust boundary is a line where data or requests cross from a less-trusted component to a more-trusted one. At a boundary, the receiving side must check what arrives or limit what it can do. Look at the five numbered connectors again.

Choose the connectors where you would draw a boundary, and write the rule each one would enforce. Two questions help. Which component processes input it did not create? And which component holds more access than its job needs?

Boundary A sits where the sandboxes' requests enter the proxy, on connector one. The sandboxes were untrusted, yet the proxy did whatever their requests asked, including fetching arbitrary addresses. Rule A: the proxy accepts only requests for approved packages, so nothing a sandbox sends reaches the rest of the internet. OpenAI's changes went further: micro virtual machines whose outbound access was at first denied entirely, and no package proxy in the research containers.

Boundary B surrounds the dataset worker, on connector four. Parsing uploads means processing input that someone else wrote. Rule B: parse inside an isolated sandbox that can read only the uploaded files, with no secrets, no network, and a sandboxed template engine.

Boundary C sits where the workers' requests enter the cluster's control interface, on connector five. Rule C: a worker's token cannot read cluster secrets, and no single shared credential holds full administrator rights. The note on the worker is different: the worker already holds those secrets, so no receiving side can refuse. That problem belongs to least privilege, in the next scene.

Test the idea with one boundary. Suppose boundary B had existed, and none of the others. Trace the chain hop by hop. How far would the attack have gone?

Boundaries decide whether an attacker can move. Least privilege decides how much it gets where it lands. Here is what a compromised dataset worker could reach: the dataset being previewed, other files on its machine, credentials for databases, messaging, code repositories, and the cloud, and through its token, a credential with full administrator rights. The note on the worker belongs here too: secrets it held all along.

The worker's job is to preview one uploaded dataset and to save that preview, so the Hub can show it. Reading the upload is clearly needed. How narrow can the saving step be?

OpenAI's report describes a contrasting episode. Another agent running code on a production dataset worker read the machine's instance metadata and obtained the node's temporary credentials. They let it read only that node and its own pod; its attempts to list wider cluster resources and to read Kubernetes secrets were denied. The administrator access had come through a different credential, a pod's service-account token. Where a credential was narrow, that path ended.

Now plan the protection for the next evaluation and the next upload pipeline. Defense in depth stacks controls that each still hold when another one fails. Each plan below stacks several controls. Which one still holds when any single control fails?

In October, OpenAI described its containment as defense in depth: sandboxes, micro virtual machines, monitoring, and network perimeters designed to hold even if all earlier controls fail. Detection counts as a layer only when someone acts on it. OpenAI's early alerts did not stop the evaluations, and the monitors that read the models' reasoning were not running on these evaluations.

Users upload profile pictures to a web app. A thumbnail service resizes each picture and stores the result; its environment contains the database administrator's password. An email service holds a key for sending mail and sends fixed welcome messages to new users.

Run the four questions of a security plan. What are you defending? Who might attack, and why? What is exposed? Then decide which component most needs isolation.
