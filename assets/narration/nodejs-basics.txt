How can Javascript read a file or answer a web request without a browser? It needs a runtime: an environment that executes the language and supplies useful tools. Node JS is that environment for a computer or server. It is not a different programming language.

Inside Node JS, V eight executes your Javascript. Node adds capabilities such as reading files and accepting network connections. A browser instead provides tools for interacting with a web page. Keep these two ideas separate: Javascript is the language; the runtime determines which tools your program can use.

Our first program greets Sam and counts the greeting. Read it from top to bottom. Const gives the text Hello the name greeting; the quotation marks make it a string. Let gives the number zero the name count. We use let because count will change. A const binding cannot be reassigned.

Next, the arrow creates a function and stores it under the name greet. Name, in parentheses, is a parameter: a name for the input the function will receive. The curly braces enclose its body. We have described the work, but have not run it. Count is still zero.

The last line calls greet. Parentheses after a function name mean run it, and Sam is the argument we pass in. Inside this call, the parameter name now refers to Sam. Execution moves into the function body.

Now we want to read a file, print its contents, and print Next. Our file, note dot text, contains Hello from disk. Assume it exists and the read succeeds. Require loads Node's built-in file-system module; we name that collection of tools fs. The dot lets us select read file sync from it.

When the call returns, text receives Hello from disk. Only now do the two console dot log calls run. First the file contents, then Next. The important cost is not just a slow file: other work needing this thread has been unable to make progress during the wait.

What if Next could print while the file is being read? This version uses read file without Sync. The file and encoding stay the same. The new third argument, on file, is a function to handle the result later. We will define it next. This call starts the operation and returns without the file text.

Javascript moves on and prints Next. Node coordinates the file operation using the operating system and a lib UV worker pool. Once our current code finishes, the Javascript thread can run other ready work. The file operation and Javascript can make progress during the same period.

When the read completes, on file becomes ready to run with the result. The event loop coordinates when ready callbacks execute. A ready callback does not interrupt Javascript already running; it must wait for that code to finish. The ready area here is a simplified view of Node's queues.

Now the callback runs and prints Hello from disk, after Next. This is concurrency: operations overlap in time. It is not two callbacks running simultaneously on this Javascript thread. A long calculation still occupies the thread and delays other callbacks, even in a program that uses asynchronous file reads.

A callback is a function you pass to other code. This snippet defines on file to handle either success or failure. Function, followed by a name, parameters, and a body, is another way to define a function. The last line passes on file to read file. There are no call parentheses after on file: we hand over the function, not the result of calling it now.

On success, Node calls our function with two arguments: null first, meaning no error, and the file text second. They become the values of error and text. The if statement tests error. Null makes that condition false, so we skip the error block and print Hello from disk.

Suppose the file is missing instead. Error now holds an error object, so the condition is true. The console dot error call reports the problem. Return exits this callback immediately, before console dot log can try to print missing data. Handling failure is part of using an asynchronous result.

Here is another way to express the same task. We load the promises version of the file-system module. Its read file returns a promise: an object representing an eventual result or failure. Calling show file starts our async function. At await, this function suspends until the promise settles; the Javascript thread can do other work.

On success, the promise fulfills with Hello from disk. The function can resume: await produces that value, text receives it, and console dot log prints it. The later step is written below the read, but it still runs only after the asynchronous result is ready.

On failure, await throws the rejection, and catch receives the error. We report it instead of printing file text. Try and catch keep those two outcomes separate. Notice what async does not do: a long calculation inside show file still occupies the Javascript thread. Await is not a command to create another thread.

Let's use a callback to answer a browser. This program loads Node's built-in HTTP module, then creates a server. The create server call receives an arrow function as its request handler. We are registering what to do later. We have not sent Hello yet, because no request has arrived.

A module is reusable code. Node already includes the file-system and HTTP modules; they need no extra installation. Express is an external package. In a project's terminal, NPM install express downloads its code into node modules and records the dependency in package dot Jason. Installing makes the package available to the project.

Remember the different jobs: NPM installs packages; require loads modules; Node runs your Javascript program.
