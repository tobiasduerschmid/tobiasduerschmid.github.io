Imagine your music app. You build a Road Trip playlist: one song to start, your whole Throwbacks playlist in the middle, and one song to end the trip. Press Play, and the queue fills in exactly that order: fourteen minutes of music.

Notice what the app treats alike. A song and a playlist both show a length, and both have a Play button. Try it: pause the narration, press Play on any song or playlist, and watch which songs fill the queue.

The Composite pattern organizes structures like this one. Its roles are a shared interface, single items that stand alone, groups that hold other items, and the clients that use them. We describe it the way every pattern is described: its context, problem, solution, and consequences. Choose a code language above; the design is the same in every language.

First, the context. The Composite pattern applies to part-whole hierarchies: wholes made of parts, where some parts are wholes themselves. A playlist is made of songs and other playlists, and those playlists are made of songs, nested as deep as you like.

The second sign: clients, the code that uses these objects, want to ignore the difference between a single object and a group. The Play button and the screen that shows lengths ask a song and a playlist the same questions. A song answers for itself; a playlist answers for everything inside it.

Such structures are everywhere: folders that hold files and folders, drawings whose shapes are grouped into larger shapes, menus with submenus, and the boxes nested inside every web page. They form trees. An item with nothing inside is called a leaf, and a group is called a composite.

Now the problem. Here is a direct implementation. Song stores a title and a length in seconds. Playlist keeps its songs in one list and its nested playlists in a second list, with a separate add method for each.

Duration adds up the songs, then asks each nested playlist for its duration. Play does the same: it queues the songs, then each nested playlist. Every operation needs two loops, one per list, and every new operation will need two more.

Now press Play on Road Trip. You added a song, then Throwbacks, then the song meant to end the trip. But play queues both songs first and Throwbacks after them. Two separate lists cannot remember the order in which you added things.

Clients suffer too. The Play button must check whether it holds a song or a playlist, because only Playlist has a play method. Every screen that shows a length repeats that check: a song stores its seconds, but a playlist computes its duration.

Your app now adds podcast episodes, and listeners want them in playlists, between songs. Before continuing, predict which code must change, and what happens if one change is forgotten. Pause here if you want more thinking time.

A third list and a third add method, a third loop in every operation, and another branch in every client check. Forget the loop in duration, and every episode silently drops out of the total time. Each new kind of item multiplies the work.

That is the problem: the code treats single items and groups differently, though listeners treat them the same. So a good solution must meet four demands: one request that works on any item, nesting to any depth, the order the listener chose, and new kinds of items without editing every loop.

Here is the fix, one class at a time. To keep songs and playlists in one ordered list, they need one shared type. Playable is that interface. It declares what listeners do with any item: ask for its duration, and play it.

Play does not return a list. It receives the play queue and adds titles to it, in order. Passing one queue down through every playlist collects all the titles without building and joining a new list at each level.

Second, Song implements Playable. Its duration returns its own length, and its play adds its own title to the queue. A song has nothing inside it, so it answers every request directly, without asking any other object.

A song stores only its own title and length. It never changes, and it knows nothing about the playlists that hold it. So one Song object can sit in Road Trip and in your gym playlist at the same time.

Third, Playlist implements Playable too, and it keeps a single ordered list of items. Each item is a Playable, so it may be a song or another playlist, and Playlist never asks which. Add appends any Playable to the end.

Duration asks each item for its duration and adds up the answers. When an item is itself a playlist, it does the same with its own items. The question travels down to the songs, and the sums travel back up.

Play passes the same queue to each item, in order. Because one list keeps the order you chose, the queue matches the playlist exactly as you built it, unlike the first design, which queued all of its own songs first.

Notice that add is declared only in Playlist. A song has no add method, so a compiler or type checker rejects adding to a song before the program runs. That is the safe choice. The price is that code adding an item must know it holds a playlist.

The other choice is transparency: declare add in Playable as well. Then every item looks alike, even to code that adds, but a song must reject a call to add while the program runs. You trade early errors for uniform code.

Now watch the objects work together on one request. Each Play button holds one Playable and never asks which kind. Press the button for Road Trip: it creates an empty queue and calls play on Road Trip.

Road Trip forwards play to its first item, the song Sunroof Down, which adds its own title. Its next item is the Throwbacks playlist. Predict: what does Road Trip send to Throwbacks, and what happens inside it? Pause here if you want more thinking time.

Road Trip sends Throwbacks the same play message it sent the song. Throwbacks forwards play to each of its own songs, and each one adds its title. The request travels down, one level at a time, until it reaches songs.

Then Road Trip plays its last song, and the call returns to the button with four titles, in the order you chose. That is the whole rule: a song answers directly, a playlist forwards to each item, and the button never asks which is which.

Now step back. Remove the songs and playlists, and four roles remain: they are the Composite pattern. The Component, like our Playable, declares the operations that single objects and groups share, so clients can use either one.

A Leaf, like our Song, has no children and implements every operation itself. The diagram draws the role once, but many classes can play it, each answering requests in its own way.

The Composite, like our Playlist, stores child components and implements each operation by forwarding it to its children, sometimes adding work before or after. The arrow with the hollow diamond and the star says that a composite holds any number of components.

The Client, like our Play button, talks only to the Component interface. Now follow the arrows around the Composite: it is a component, and it holds components. That cycle in the diagram is what lets groups contain groups, to any depth.

Now the consequences, starting with the benefits. Clients become simple: the Play button treats a song and a playlist of playlists the same way, so the type checks from the problem are gone. And wherever code expects a single item, it can take a whole playlist instead.

New kinds of items are easy to add. Any new leaf or group class that keeps the shared interface works inside existing playlists, and existing clients handle it without a change. The code that combines items is written once, in Playlist.

The liabilities. The design can become overly general. Suppose albums, a kind of playlist, may hold only songs. Album inherits add, which accepts any Playable, so the type system cannot keep an episode out of an album; the album has to check each item while the program runs.

And the choice about add costs something either way. Declared only in the composite, add is checked before the program runs, but code must know it holds a composite before adding. Declared in the component, every object looks alike, but leaves must reject add while the program runs.

With those trade-offs in mind, revisit the context. Use Composite when items really nest inside groups, and groups inside groups, and clients should not care whether they hold one item or a group. If groups never nest, a plain list of songs is simpler.

Check the parts, too. If every item has the same data and only some have children, one class with an optional list of children can play every role; separate leaf and group classes would add nothing. They pay off when single items and groups behave differently and new kinds keep arriving.

Composite also hides inside other patterns. In Model-View-Controller, views nested inside views form a composite, and a macro command made of commands is one too. Decorator looks similar but differs in purpose: a decorator wraps one object to add behavior, while a composite holds many to treat them as one.

Add an Episode class that implements Playable: a new leaf. Its duration returns its length, and its play adds the show and the title. Playable, Song, Playlist, and the Play button stay unchanged; only code that creates episodes knows the new class. The first design needed a new list, loop, and check everywhere.

To finish, recall the whole pattern. Context: a part-whole hierarchy that nests, whose clients want to treat one object and a group alike. Problem: code that handles single objects and groups separately repeats its loops and type checks, and breaks as new kinds arrive. Solution: a Component interface, which Leaves implement directly and Composites implement by forwarding to their children. And the consequences: simple clients and easy new kinds, at the cost of an overly general structure and a choice between safety and transparency. The summary quiz checks each part on a new example.
