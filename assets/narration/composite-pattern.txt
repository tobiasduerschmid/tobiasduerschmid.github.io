The Composite pattern organizes structures like this one. Its roles are a shared interface, single items, groups that hold other items, and the clients that use them. We describe it by its context, problem, solution, and consequences. Choose a code language above; the design is the same in each.

First, the context. The Composite pattern applies to part-whole hierarchies: wholes made of parts, where some parts are wholes themselves. The story is made of tiles. Its right half holds the cat and the bottom split, and the bottom holds two photos. Splits nest as deep as you like.

The second sign: clients, the code that uses these objects, want to ignore the difference between a single object and a group. The Share button and the layout tree ask a photo and a split the same questions. A photo answers for itself; a split answers for everything inside it.

Such structures are everywhere: folders that hold files and folders, drawings whose shapes are grouped into larger shapes, menus with submenus, and the boxes nested inside every web page. They form trees. An item with nothing inside is called a leaf, and a group is called a composite.

Now the problem. First, a small helper every version uses. An area is a rectangle that cuts itself into equal parts, side by side or stacked. A split cuts its area into one part per item and hands each item its part of the area, in list order.

Here is a direct first design. A photo has a name. A split has a direction and one list of items, and each item is either a photo or a split. The two classes share no type, so the split holds two unrelated kinds of items.

So every operation asks which one it holds. The split's draw method draws a photo itself, or forwards the part to a nested split. Its photo count adds one for a photo, or asks the nested split for its count. Each operation repeats the same check.

The Share button asks too: is my selection a photo or a split? If it is a photo, the button draws the photo itself, into the whole story. So the knowledge of how to draw a photo is now written in two places, the split and the Share button.

The item type must allow captions, and all three checks need a new branch: in the split's draw method, its photo count, and the Share button. Miss the one in draw, and the caption's area stays blank. Nothing reports an error, because that check has no else branch.

So a solution must meet four demands. One shared type for photos and splits. A split that holds one ordered list of that type, so splits nest without checks. A Share button that works on any tile without checks. And new kinds of tile without edits to existing classes.

Solution, concretely. First, one shared type. Tile declares the two requests that every tile answers: draw yourself into this area, and tell me your photo count. Photo and Split both implement Tile, so code that holds a tile no longer needs to know which kind it holds.

Look at draw's canvas parameter: a list that collects one line for each tile drawn. The same canvas is handed down the whole tree, so every tile adds its own line, and whoever called draw gets the finished picture back in one list.

Photo answers both requests from its own data. Its draw adds one line to the canvas: its name and the area it was given. Its photo count is simply one. A photo has nothing inside, which makes it a leaf of the tree, and it never asks anyone else.

A photo never changes after it is made, and it knows nothing about the split that holds it. So one photo object can appear in two stories at once: the beach photo in your summer dump and in a best-of-the-year story, both drawing the same picture.

Split keeps a direction and one ordered list of tiles. Because the list's type is Tile, not photo-or-split, a split can hold both kinds mixed, in any order, and splits nest inside splits without a single type check. The list's order is the reading order of the story.

Its photo count asks each of its tiles for their count and adds up the answers. It never asks what kind of tile it is holding. A nested split answers the same way, so the question travels down the tree, and the sums come back up.

Its draw cuts its area into equal parts, one per tile, and forwards each part to its tile, in list order. So list order decides where each tile lands: the first tile gets the left or top part. A split draws nothing itself; it only arranges.

Notice where the add method is declared: in Split, not in Tile. Code cannot add a tile to a photo; that mistake is caught before the program runs. That is the safe choice. The price is that code that adds tiles must know it holds a split.

The other choice declares the add method in Tile itself. Then every tile looks alike to clients, but a photo must refuse to add anything while the program runs. That is the transparent choice. This lesson's code makes the safe one; both are versions of the Composite pattern.

The call returns to the Share button with a canvas of four lines, in reading order. That is the loop of this pattern: a composite forwards each request to its children, and a leaf answers it directly. One call on the story reached every tile.

Now the solution, abstracted. Remove the photos and the story, and four roles remain. The Component, our Tile, declares the requests that every object in the structure answers, whether it is a single item or a group. Clients hold Components and never need to know which kind they hold.

A Leaf, our Photo, answers each request itself and has no children. A structure can have many kinds of leaves; each kind implements the Component in its own way, and nothing above it needs to know which kind it is.

A Composite, our Split, holds children of the Component type and answers by forwarding to them, sometimes adding work of its own. Because a Composite is itself a Component, Composites can contain Composites: these four classes describe object trees of any depth.

The Client, our Share button, uses only the Component interface. It never asks which kind it holds, so the same call works on one photo or on the whole story, and the client stays this simple however deep the tree grows.

Now the consequences. The first benefit: simple clients. The Share button treats one photo and a whole split exactly the same way, with no type checks at all. Wherever a single tile fits, a whole split of tiles fits too, and the button's code never grows.

The second benefit: new kinds fit in. A new kind of tile is one new class that implements Tile. Existing splits hold it and the Share button shares it, without editing any existing class. And a new kind that forgets draw is reported as an error, not left blank.

The first liability: the design can be overly general. Imagine a photo-booth strip, a kind of split that may hold only photos. It inherits the add method from Split, which accepts any tile, so the type system cannot keep splits out. The strip needs a check while the program runs.

The second liability: safety or transparency. With the add method only in Split, misuse is caught before the program runs, but code that builds the tree must know it holds a split. Declared in Tile, it makes all tiles look alike, but leaves must reject it while the program runs.

Back to the context, and when to use the pattern. Composite fits when parts nest inside wholes, wholes nest inside wholes, and clients should not care whether they hold one item or a whole group. The summer story fits: splits sit inside splits, and one Share button serves every tile.

Compare a carousel post: a flat list of photos you swipe through. Nothing nests, and nothing treats one photo and the whole carousel alike, so a plain list is better. With one kind of leaf and no others coming, one Tile class with optional children can be simpler too.

To finish, recall the whole pattern. First, the context: parts nest into wholes, and clients treat one object and a group alike. Then the problem: code that asks every item for its type repeats its checks and silently misses new kinds. Then the solution: a Component interface that Leaves implement directly and Composites implement by forwarding to their children. And the consequences: simple clients and easy new kinds, but an overly general structure and a choice between safety and transparency.
