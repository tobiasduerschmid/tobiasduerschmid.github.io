Therack twenty five was a computer-controlled machine used to treat cancer with radiation. A therapist entered a prescribed treatment at a keyboard and screen, called the console. The patient received radiation from the treatment head. Follow the arrows: the first arrows carry information; the last arrow represents a physical beam.

The prescription specified the intended treatment, including the kind of radiation and the dose. Absorbed dose is radiation energy deposited per unit mass of tissue. The controller was the software that prepared the equipment and managed delivery. Typing a request did not itself deliver radiation. Our debugging question will be how a reasonable request could lead to an incorrect physical result.

An accelerator gives electrons energy, producing an energetic beam. Both treatment modes began with that electron beam. In electron mode, abbreviated E, the machine spread that electron beam across the treatment field at appropriate settings. In this diagram, read each arrow as the path of the beam. We show only the parts needed to understand the difference between modes.

In X-ray mode, abbreviated X, the electrons instead struck a metal target inside the treatment head, producing X-rays. Here, target means a machine part, not the tumor. This conversion required a substantially more intense electron beam. Changing between E and X therefore required changing both beam settings and the physical arrangement.

If X-ray-production settings remained while the required metal target was absent, intense electrons could reach the patient inappropriately. That is the mismatch we need to understand. Remember two questions: what settings has the machine applied, and what is actually in the beam path? The displayed choice alone cannot answer both.

This sequence diagram shows a successful setup with an unchanged E request. Each vertical lane represents a responsibility. Read events from top to bottom. An arrow shows an interaction; a return arrow reports a result. Our simplified example first prepares the beam settings, then the physical arrangement. It does not claim the historical program used these exact calls.

Both preparations must be suitable for the current request before treatment proceeds. A ready indication means the controller is allowing the next step; it is a claim to examine, not independent proof of physical correctness. The operator's command to turn the beam on comes after preparation. None of the setup arrows in this diagram delivers radiation. Keep three facts separate: requested mode, applied configuration, and permission to operate.

So far the request stayed unchanged. But the interface allowed the therapist to correct an entry. Setup took time, and software could handle keyboard input while other preparation remained unfinished. We will first establish what happened, then compare ordinary setup with a correction during that work. The first decision begins with the reported evidence.

In Tyler, Texas, two incidents occurred in 1986. Patients reported unexpected painful effects during treatment, while the console displayed a low dose and a cryptic numbered warning. The machine paused, but its interface allowed the operator to proceed. A low reading could suggest little radiation had been delivered; the patient's experience challenged that interpretation.

Before following the software, state what correct operation requires. The request expresses the intended treatment. Beam setup chooses operating settings. Positioning selects the arrangement in the beam path. These are different responsibilities. A completed setup routine tells us about its own work; it does not automatically tell us what another responsibility has done.

Imagine the console now says E. We need evidence about whether treatment may proceed, not just evidence that the text on screen changed. Use the two preparation paths in the diagram to decide what must be established for the current request.

Routine checks initially failed to reproduce the reported event. Investigators also considered an electrical shock, without substantiating that explanation. Reconstructing a rapid change from X to E helped investigators reproduce the Tyler problem. We now ask how that history could matter. The controller had one computer, but several software tasks took turns running. A task could pause while input handling changed a shared value, then resume. Two processors are not required for this kind of timing problem.

The Shared request lane stands for information in memory. Beam setup reads X and uses it to select settings. The therapist then changes the shared request to E. Changing that memory value does not undo a decision already made from its earlier value. Follow the arrows down to the correction; the positioning read has not yet happened.

Positioning is about to read the current request. No step recomputing earlier settings is shown. What combination of decisions is now possible? Also separate internal preparation from physical output: inhibited means operation is not permitted.

Positioning can select the E arrangement while the beam settings still come from X. The next question is why the controller failed to notice and reconcile the correction. Reconcile here means revisiting earlier work so that it agrees with the current request. The diagram explains inconsistent decisions; it does not yet show permission to deliver a beam.

Part of setup adjusted bending magnets that steer the electron beam. This took several seconds. During the wait, a delay-checking routine could look for corrected input. A software flag is a stored value used as a yes-or-no condition. Here, flag on meant magnet setup was in progress, and later edit checks depended on that flag being on.

Now follow the sequence. The first delay clears the flag, meaning it sets the flag to off, although magnet setup continues. An input correction arrives afterward. A later delay checks for edits only when the flag is on. What can happen to this accepted correction? The corrected input and the flag are separate stored values.

The later edit check can be skipped because the flag is already off. There was also a completion problem. The interface had an area for commands after treatment entry. Reaching it once was treated as evidence of completion, even if the therapist went back to edit. Past completion did not establish that editing was finished now.

Use The Debugging Book's terms. The implementation defect is the incorrect rule, such as clearing the setup flag too early. The resulting incorrect runtime state is a fault, also called an infection. Incorrect physical output is a failure; injury is its consequence. A wrong internal state can exist before any external failure occurs.

A diagnosis needs two parts: how this sequence causes the invalid state, and why accepting that state violates the requirement. Recall the requirement: applied settings and positioning must be suitable for the current request before operation. Which explanation connects the mechanism to that requirement? Typing speed identifies a trigger; it does not itself explain an implementation defect.

To reason about a repair, switch to a state diagram. Each box describes a condition of our proposed controller. Inhibited means operation is blocked. Preparing means setup is underway. Ready means permission has been granted. Arrows show changes of state. Text in square brackets is a guard: a condition that must be true for that change to happen.

This is a new teaching design, not a recovered diagram of Therack twenty five. Starting setup moves from Inhibited to Preparing. Completing work might move to Ready, but the guard is deliberately missing. An edit after Ready revokes permission. Work based on an older request is obsolete: finishing it does not make it suitable for the newer request.

Adding a delay might avoid one observed timing. It would not explain what to do if another correction arrived. What must the completion rule establish before granting permission? Choose a relationship between the work, the current request, and the equipment, rather than a waiting time.

The proposed rule authorizes only a current, consistent configuration. The larger box groups Preparing and Ready: an edit in either state invalidates permission. Text after a slash names the action taken. Historically, the Tyler corrections kept the magnet flag on until setup ended and added shared editing status to prevent premature progression. Those were specific changes implementing related obligations.

Suppose the original bad sequence is now blocked. That is necessary, but a controller that never permits anything would pass that test too. Which additional test establishes that intended use still works? After answering, consider edits after readiness and old work finishing late. Old results must not displace a newer valid setup.

A later accident at Yakima in 1987 involved a different defect. Inside the treatment head, a turntable selected components in the beam path. This was not the patient's table. Its field-light position used visible light to help align the treatment field; it was not a treatment position. A SET request asked the mechanism to return toward the treatment configuration. SET did not turn the beam on.

Before progressing, software needed to check position. Follow three separate steps: setup requests a check; the checker inspects position and records a blocking problem if needed; progression consults that recorded status. The check request was stored in a one-byte value. Nonzero meant perform the check. A byte can represent 256 different values, here zero through 255.

The program repeatedly added one to that value during setup passes. These are repetitions inside preparation, not counts of patients. The arithmetic wraps: adding one beyond the largest representable value starts again at zero. In our paused trace the value is 255, and the next pass increments it. Predict the next value and what the nonzero guard will do.

The value becomes zero, so the position check can be skipped. The later decision uses a separate blocking-status value. Think of that status as stored yes-or-no problem indicators. If no blocking indicator is set, the software may advance. But that does not tell us whether a required check just ran or was skipped.

In the published explanation, the turntable was still in field-light position. A SET request occurred during the zero interval, while other blocking indicators remained clear. Under those conditions, setup could advance to the next phase with the wrong physical arrangement. Wrapping alone does not explain an overdose. Skipping a check also does not erase a problem already recorded.

The value was being used to say check required, not to count useful events. If every setup pass must leave it nonzero, how should that value be updated? Compare enforcing its intended meaning with merely making the wraparound take longer. This repairs one local obligation; the complete machine needs more evidence.

A software repair addresses a known mechanism. A protective function adds another way to prevent unsafe output.
