# C4 model feature: decisions and open items

This is the tracked record of the decisions behind the C4 model feature: the SEBook chapter, the ArchUML C4 toolkit (core, renderer, editor), and the two tutorials. It is distilled from the working records of the implementation runs, which are not kept in the repository, from the instructor decisions in the main spec, and from the routing redesign.

- Main spec: [`docs/superpowers/specs/2026-11-08-c4-model-design.md`](superpowers/specs/2026-11-08-c4-model-design.md). Its tables D1–D10 (decisions taken with the user) and J1–J14 (decisions delegated to the designer) and its §17 (changes after review) are the binding text; this document cites them and does not replace them.
- Routing design: [`docs/superpowers/specs/2026-11-09-c4-routing-redesign.md`](superpowers/specs/2026-11-09-c4-routing-redesign.md).
- Editor host contract: [`docs/c4-editor.md`](c4-editor.md).
- UML-view editing design: [`docs/superpowers/specs/2026-11-12-c4-uml-view-editing.md`](superpowers/specs/2026-11-12-c4-uml-view-editing.md) (revision 3.2) and its plan `docs/superpowers/plans/2026-11-12-c4-uml-view-editing.md`; its decisions are the entries UV-1 to UV-16.
- Plans: `docs/superpowers/plans/2026-11-08-c4-{core,interfaces,rendering,editor,chapter,tutorial}.md`.

## How to read an entry

Each entry has an id, the date it was taken, and five parts:

- **Decision**: what was decided.
- **Why**: the reason that carried it.
- **Rejected**: the alternatives that were considered and turned down. "None recorded" means the records name no alternative.
- **If wrong**: the cost of reversing it later.
- **Where**: the spec section, code, and tests that hold it.

Decisions marked *(user)* were taken with the user or the instructor. Decisions marked *(on behalf of the user)* were taken by the implementation controller for the user and are listed again under [Decisions to confirm](#decisions-to-confirm). All other decisions were delegated.

Paths under `js/ArchUML/` live in the ArchUML submodule, a separate repository. File names are those of 2026-11-11, after a behaviour-preserving split with the same public API: `c4-edit.js` is a facade over `c4-edit-splices.js`, `c4-edit-results.js`, `c4-edit-references.js`, `c4-edit-elements.js`, `c4-edit-sections.js`, and `c4-edit-interfaces.js`; placement runs through `c4-place-frame.js`, `c4-place-ranks.js`, `c4-place-corridors.js`, `c4-place-cross.js`, and `c4-place-settle.js`; and the interface card and the shared markup moved from `c4-render.js` into `c4-card.js` and `c4-markup.js` (main spec §3, routing spec §3.1). Code named below as in `c4-edit.js`, `c4-place.js`, or `c4-render.js` may now sit in one of those files. Since 2026-11-12, routing likewise runs through `c4-route-frame.js`, `c4-route-shapes.js`, `c4-route-labels.js`, `c4-route-candidates.js`, `c4-route-costs.js`, `c4-route-state.js`, `c4-route-pricing.js`, `c4-route-separate.js`, `c4-route-select.js`, `c4-route-growth.js`, and `c4-route-evidence.js` behind the same `ArchUMLC4Route` API, so code named below as in `c4-route.js` may sit in one of those.

## Schema and core

### SC-1 A clean new schema, `c4-design/1`

- **Date:** 2026-11-08 *(user; spec D1)*
- **Decision:** `design.yml` gets a new schema. Existing CS 188 `design.yml` files are not supported; loading one gives a dedicated error message. After the design review, `web_app` became `browser_app`, `in_enterprise` and top-level `groups` were added, `hosts` accepts systems, and infrastructure nodes are leaves.
- **Why:** The old format was built before C4 and RDD were its organising ideas. Brown separates server-side and client-side web apps, and ownership and organisation are independent axes.
- **Rejected:** Compatibility with the CS 188 files.
- **If wrong:** A converter for old files; the schema itself would not change.
- **Where:** Spec §4, §17. `js/ArchUML/c4/c4-schema.js`, the versioned JSON Schema under `js/ArchUML/c4/schema/1/` (generated by `toJsonSchema`). Tests: `js/ArchUML/tests/c4/schema.test.js`, `model-structure.test.js`.

### SC-2 All reusable code in ArchUML; the site keeps thin adapters

- **Date:** 2026-11-08 *(user; spec D3, J1)*
- **Decision:** The core, renderer, editor, schema, and CLI live in the ArchUML submodule. The core is DOM-free. The site has adapters only (`js/c4-editor-site.js`, `js/c4-editor-link.js`, `js/tutorial-c4.js`). A VS Code extension is designed for (host contract, DOM-free core, versioned JSON Schema, CLI, fake-host and strict-CSP tests) but not built.
- **Why:** The user asked for an editor a VS Code extension can host later. Readiness costs little; an extension is a separate product.
- **Rejected:** Site-owned C4 code; building the extension now.
- **If wrong:** Moving modules between repositories.
- **Where:** Spec §3, §3.5. `js/ArchUML/c4/`, `js/ArchUML/c4/cli.js`, [`docs/c4-editor.md`](c4-editor.md) "The VS Code path". Tests: `js/ArchUML/tests/c4/cli.test.js`, `tests/c4-editor-contract.spec.js`.

### SC-3 One manifest fixes the load order of the hand-written modules

- **Date:** 2026-11-08 (spec §17)
- **Decision:** The C4 files are UMD modules without a bundler. `js/ArchUML/c4/manifest.json` lists the `core`, `render`, and `editor` files in load order, and every loader reads it: the bundle stub's lazy loader, the static prerender (`uml_to_svg.js`), the site includes (`_includes/c4-scripts.html`, `_includes/c4-editor-scripts.html` through the `_data/archuml_c4_manifest.json` symlink), and the tutorial popout. Editor modules look up their siblings at call time, so insertion order never breaks loading.
- **Why:** Hand-maintained UMD files need a strict order, and four loaders must agree.
- **Rejected:** A load order defined inside the renderer (the first draft of §3).
- **If wrong:** Introducing a bundler step.
- **Where:** Spec §3, §3.1. Tests: `js/ArchUML/tests/c4/bundle-stub.test.js` (the stub's list equals the manifest), `scripts/tests/c4-site-registration.test.js`, `scripts/tests/uml-static-plugin.test.js` (the real manifest's files are fingerprinted inputs of the prerender cache).

### SC-4 A vendored, pinned YAML parser

- **Date:** 2026-11-08 (spec §15)
- **Decision:** The core parses YAML with the `yaml` package at version 2.9.1, vendored with integrity hashes.
- **Why:** The core must run in the browser, in Node, and in a future VS Code webview without a network fetch, and it needs source positions for diagnostics and text splices.
- **Rejected:** None recorded.
- **If wrong:** Swapping the parser behind `js/ArchUML/c4/c4-yaml.js`, the only module that touches it.
- **Where:** `js/ArchUML/vendor/yaml/2.9.1/`, `package.json` devDependency. Test: `js/ArchUML/tests/c4/vendor-yaml.test.js`.

### SC-5 Edits are text splices, and one gesture is one undo step

- **Date:** 2026-11-08 (spec §4.9, §17; `batch` added the same day after the user's drag-first direction)
- **Decision:** Every edit command returns a splice of the source text, so comments, ordering, and untouched lines survive. A `batch` command combines several commands into one common-prefix/suffix splice. Composite editor actions that need an id the core generates first run the command as a pure dry run to learn the id, then dispatch one `batch`.
- **Why:** Re-printing the whole document rewrites lines the learner never touched. Drag gestures such as "drop from the palette and pin" are several commands and must be one undo step in Monaco and in VS Code.
- **Rejected:** Re-printing the document from the model; an id-returning core API for composite actions.
- **If wrong:** None for `batch` (an extra command).
- **Where:** `js/ArchUML/c4/c4-edit.js`, `c4-yaml.js`; `js/ArchUML/c4/editor/c4-editor-state.js`. Tests: `js/ArchUML/tests/c4/edit-elements.test.js`, `edit-details.test.js`, `yaml-adapter.test.js` (property and metamorphic tests), `editor-state.test.js`.

### SC-6 Selector identity: keywords loose, ids exact

- **Date:** 2026-11-08, re-confirmed 2026-11-09
- **Decision:** In view selectors and layout keys, keywords are case-insensitive; element, scenario, environment, and custom-view ids are matched exactly; interface ids are matched ignoring case. One grammar in `c4-schema.js` serves projection, layout keys, queries, and the editor.
- **Why:** Ids are YAML keys, which are case-sensitive. The C4 tutorial's selector-typo exercise depends on a wrong-case id failing. The first build of the core lowercased ids, against its own spec; that was corrected.
- **Rejected:** Case-insensitive ids (the first build); two grammars with two object shapes.
- **If wrong:** An embed with a wrong-case id shows the error figure.
- **Where:** Spec §4.10, §5.1. `js/ArchUML/c4/c4-schema.js` (`selectorKey`), `c4-projection.js`. Test: `js/ArchUML/tests/c4/projection-selectors.test.js`.

### SC-7 ArchUML text uses sanitised aliases

- **Date:** 2026-11-08
- **Decision:** The UML text the core generates (`toUml`) uses aliases restricted to letters, digits, and `_`, with `_2`, `_3` for collisions; labels keep the original names.
- **Why:** The ArchUML parsers do not guarantee hyphens in alias tokens.
- **Rejected:** Raw ids as aliases.
- **If wrong:** "Copy ArchUML" output shows slightly different aliases.
- **Where:** `js/ArchUML/c4/c4-uml.js`. Test: `js/ArchUML/tests/c4/uml.test.js`.

### SC-8 A predicate about something the learner has not built fails; it is not an author error

- **Date:** 2026-11-08
- **Decision:** A tutorial predicate that names a view, scenario, or element missing from the learner's model returns `{passed: false, message}` with a learner-facing message (for example "No view named who-decides yet"), and hint conditions on unresolved ids are silently false. Only malformed predicate keys, malformed selector syntax, and the configured `c4.view` are author errors. New queries `step` and `requirement` were added; `owns_any` is a name lookup with substring matching.
- **Why:** Learners build the model step by step; a missing piece is the normal state, not a broken tutorial.
- **Rejected:** Treating unresolved names as author errors.
- **If wrong:** Some author typos surface as learner failures; the content test catches them before release.
- **Where:** Spec §7.3, §8. `js/ArchUML/c4/c4-query.js`. Tests: `js/ArchUML/tests/c4/query.test.js`, `scripts/tests/c4-hint-conditions.test.js`.

### SC-9 Scenario semantics: replies and fragments

- **Date:** 2026-11-08
- **Decision:** A reply may answer a forward step that precedes its enclosing fragment. Each fragment branch starts from a copy of the open requests, so a reply in one branch does not consume a request for a sibling branch. Replies are restricted to synchronous relationships; queues and topics get deliveries instead.
- **Why:** The tutorial's seat-hold failure branch needs a reply inside an `alt` that answers a request made before it.
- **Rejected:** Requiring every reply inside the fragment that holds its request.
- **If wrong:** One rule in step classification.
- **Where:** Spec §6.3. `js/ArchUML/c4/c4-projection.js` (step classification). Test: `js/ArchUML/tests/c4/projection-uml.test.js`.

### SC-10 Learner messages follow a reviewed table; tests assert rule ids, not wording

- **Date:** 2026-11-09
- **Decision:** The messages of the rules that the novice profile shows or that tutorial steps raise to warnings follow the learner-message table in spec §7.2, using only terms the chapter teaches. `rdd/uncovered-requirement` no longer equates tracing with meeting a requirement, and `rdd/centralized-control` no longer claims delegation is easier to change. Editor tests assert diagnostics by rule id, severity, and quoted subject, never by full wording.
- **Why:** The alignment review found core messages that used untaught terms or overclaimed. Wording will keep improving; tests should not break when it does.
- **Rejected:** Pinning message text in editor tests.
- **If wrong:** None.
- **Where:** Spec §7.2. `js/ArchUML/c4/c4-checks.js`. Test: `js/ArchUML/tests/c4/checks-messages.test.js`.

### SC-11 The first fixture is frozen; the reference model lives in the include

- **Date:** 2026-11-08 *(spec J13)*
- **Decision:** `js/ArchUML/tests/c4/fixtures/course-registration.yml` keeps the reference model as it stood before interfaces and the chapter amendments; a test pins its SHA-256. The current reference model (spec §4.2, with interfaces and the amendments) is `_includes/c4-models/course-registration.yml`, and its test copy is `course-registration-interfaces.yml`.
- **Why:** Changing a fixture under running tests silently changes what their text edits and property runs exercise.
- **Rejected:** Re-syncing the first fixture with §4.2.
- **If wrong:** None; the two fixtures test different things.
- **Where:** Spec J13, §4.2. Tests: `js/ArchUML/tests/c4/interfaces-invariants.test.js` (SHA), `scripts/tests/c4-site-registration.test.js` (the include equals the interfaces fixture).

### SC-12 The reference model must not contain what the chapter teaches against

- **Date:** 2026-11-08
- **Decision:** Four amendments to the §4.2 model: FR-07 is about prerequisites and the unit cap; the browser sends HTTPS requests to the ingress; the API pod's technology is "Kubernetes pod"; the code-view label is "delegates each eligibility check to". The deployment projection draws no derived browser-to-pod path when an explicit node route through the ingress connects the same nodes.
- **Why:** The chapter's accuracy review found these defects in the model the chapter uses as its example.
- **Rejected:** Keeping the model and explaining the defects in prose.
- **If wrong:** Small fixture edits.
- **Where:** Spec §4.2, §6.3. `js/ArchUML/c4/c4-projection.js`; `_includes/c4-models/course-registration.yml`.

### SC-13 Core corrections from validating the drafts against the real core

- **Date:** 2026-11-10
- **Decision:** View predicates use what each notation actually draws; `check()` reports a broken saved view once; `same_as_seed` compares the parent and its own YAML including children, while dangling references stay `model/unknown-reference`.
- **Why:** The chapter's real-core validation found three places where the core disagreed with the drafted tutorial behaviour.
- **Rejected:** Changing the tutorial to match the old behaviour.
- **If wrong:** Small rule changes.
- **Where:** `js/ArchUML/c4/c4-query.js`, `c4-checks.js`. Test: `js/ArchUML/tests/c4/core-fixes.test.js`.

### SC-14 Design choices are recorded in the model; `connector:` replaces `async:`

- **Date:** 2026-11-08 *(user; spec D8)*
- **Decision:** Systems, containers, components, code elements, and collaborators accept an optional `choices:` block with `technology` (`{chosen, alternatives, because, decision}`), `styles`, `patterns` (`"Pattern"`, `"Pattern: Role"`, or `{pattern, role, instance, decision}`), and `tactics`. A relationship's kind is `connector:` with five values: `call` (the default), `message`, `event`, `stream`, and `shared-data`; `message`, `event`, and `stream` are asynchronous and drawn dashed. The earlier boolean `async:` flag is gone.
- **Why:** The decision table states no reason. What the spec builds on it: a model that records *why* an element or relationship looks as it does (checked by the `choices/*` rules, which test pattern roles against a catalog from the SEBook chapters), and a connector kind rich enough for synchrony-aware edge merging and the `interface/style-mismatch` check, which a yes/no flag cannot express.
- **Rejected:** The `async:` flag on relationships.
- **If wrong:** A schema change in `c4-design/1` and in every shipped model and tutorial solution that uses `connector:` or `choices:`; the `choices/*` rules and the connector-based checks would change with it.
- **Where:** Spec §1 (D8), §4.6, §4.7, §7.2. `js/ArchUML/c4/c4-schema.js` (design slots, collaborator keys, the `choices` and connector definitions), `js/ArchUML/c4/c4-checks.js` (`choices/*` rules). Tests: `js/ArchUML/tests/c4/schema.test.js` (connector values and their synchrony), `js/ArchUML/tests/c4/model-structure.test.js` (choices normalisation and unknown keys), `js/ArchUML/tests/c4/checks-rdd.test.js` (rule catalog). Chapter: `SEBook/architecture/c4.md`, "Collaborations Become Relationships" (`connector: message`) and "Recording Choices and Decisions".

## Interfaces

### IF-1 `provides` grows into interface descriptions

- **Date:** 2026-11-08 *(user; spec D9, after lecture L14)*
- **Decision:** An element's `provides` holds interface descriptions with a syntactic view (operations, inputs, outputs, typed fields with constraints) and a semantic view (purpose, side effects, restrictions, errors, examples, meanings, units, formats, value meanings, a model-wide vocabulary). The list of signature strings stays valid as a shorthand. Relationships name the interfaces they `uses`; operations name the responsibilities they `realizes`.
- **Why:** The lecture teaches that an interface has syntax and semantics; the model should let learners write both.
- **Rejected:** Keeping `provides` as signature strings only.
- **If wrong:** The shorthand keeps old models valid either way.
- **Where:** Spec §4.11. `js/ArchUML/c4/c4-schema.js`, `c4-model.js`. Tests: `js/ArchUML/tests/c4/interfaces-*.test.js`.

### IF-2 Interface ids share the element namespace; one `uses` rule

- **Date:** 2026-11-08 *(spec J7)*, implementation 2026-11-09
- **Decision:** Interface ids share the element id namespace (compared ignoring case), so `uses` refers to an interface without a path. A relationship from S to T may use an interface of T, of a descendant of T, or of an ancestor of T that is not S or an ancestor of S; S's own `event` or `stream` interface; or, for a queue or topic T, an interface of another element that has its own relationship to T. One pure function, `useKind`, implements the rule for the diagnostics, the `setUses` edit, and the editor's Uses picker. An interface may reuse its own provider's id, so expanding a shorthand keeps `uses` references valid.
- **Why:** A container's API is handled by one of its components (UML delegation); in publish-subscribe the publisher owns the event contract while the arrows point at the topic. Three copies of the rule would drift.
- **Rejected:** Path-qualified interface references; separate implementations per caller.
- **If wrong:** None for the single function.
- **Where:** Spec J7, §4.11. `js/ArchUML/c4/c4-model.js` (`useKind`). Tests: `js/ArchUML/tests/c4/interfaces-references.test.js`, `interfaces-edit.test.js`.

### IF-3 Interfaces appear only when a view asks; they are not a C4 abstraction

- **Date:** 2026-11-08 *(spec J8, J14)*
- **Decision:** Boxes and arrows show interfaces only with `annotations: [interfaces]` or the selector suffix `with interfaces`; the dedicated interface views always show them. Interfaces never appear in the level navigation, the level toggles, or the containment outline. In annotated dynamic views, a message label gains " (<syntax>)".
- **Why:** Brown's level discipline: APIs and payloads distract on context and container views unless they are the question. Existing renders stay unchanged.
- **Rejected:** Always drawing interfaces; treating them as a fifth abstraction level.
- **If wrong:** A default change in projection.
- **Where:** Spec J8, J14, §5.2 item 12. `js/ArchUML/c4/c4-projection.js`. Test: `js/ArchUML/tests/c4/interfaces-projection.test.js`.

### IF-4 Two interface views: a UML component view and an HTML card

- **Date:** 2026-11-08 *(spec J10, J11)*
- **Decision:** `interfaces of <element>` is a UML component diagram with provided and required interfaces inside a C4 title, legend, and notes. `interface <id>` is a card selected by the interface id alone (`interface <id> of <element>` is an accepted, checked synonym). The card is semantic HTML (an article with labelled groups, definition lists, and a field table per type), not SVG.
- **Why:** Interface ids are model-wide, so the provider adds nothing to identity. The card is a document: as HTML it inherits paragraph size, reflows, honours text spacing, exposes its structure, paginates in print, and needs no second text version.
- **Rejected:** An SVG card.
- **If wrong:** A second card renderer.
- **Where:** Spec §5.3, §6.6. `js/ArchUML/c4/c4-render.js` (card). Tests: `scripts/tests/c4-interface-card.test.js`, `scripts/tests/c4-interface-render.test.js`, `tests/c4-display.spec.js`.

### IF-5 `realizes` names the provider's own obligations

- **Date:** 2026-11-08 *(spec J12)*
- **Decision:** An operation's `realizes` names the provider's own responsibilities, or a descendant's responsibility that refines one of them. An operation realizes R when it lists R, or when the responsibilities it lists together cover every direct refinement of R, recursively.
- **Why:** RDD contracts advertise the provider's obligations, never its private implementation (Wirfs-Brock and McKean 2003; Parnas 1972). Refinement is partial, so one refinement does not stand for its parent.
- **Rejected:** Allowing any responsibility in the model.
- **If wrong:** One rule (`model/realizes-owner`).
- **Where:** Spec J12, §4.5, §4.11. `js/ArchUML/c4/c4-checks.js`.

### IF-6 Interface code stays in the existing core modules

- **Date:** 2026-11-08 *(spec J9)*
- **Decision:** Interface support was added to the existing core modules; the core manifest did not change.
- **Why:** The renderer milestone, running in parallel, embedded a copy of the core list in the bundle stub; a new core file would have broken that equality test mid-flight.
- **Rejected:** A separate `c4-interfaces.js`.
- **If wrong:** A later split (the behaviour-preserving split of 2026-11-11 is such a step).
- **Where:** Spec J9.

### IF-7 Interface rules fire only on models that use interfaces

- **Date:** 2026-11-08 (spec §7, §15)
- **Decision:** The `interface/*` rules run only once a model declares a full-form interface or a `uses`. A malformed `uses` entry is reported as `schema/value` at the entry. The novice profile defers incompleteness rules for an interface until it loses focus.
- **Why:** Interface descriptions enlarge the schema learners meet; models without interfaces must not gain warnings.
- **Rejected:** Running interface rules on every model.
- **If wrong:** None.
- **Where:** Spec §7.2. `js/ArchUML/c4/c4-checks.js`. Test: `js/ArchUML/tests/c4/interfaces-checks.test.js`.

## Rendering and routing

### RR-1 One embedding format, with comment directives

- **Date:** 2026-11-08 *(user; spec D2)*; directives 2026-11-09
- **Decision:** A C4 figure is `design.yml` content plus a `view:` selector, in a `c4` fence or a `data-uml-type="c4"` container. `_includes/c4-view.html` builds such a fence from a model file and writes its options as comment lines: `# caption:` first (the shared caption extractor reads only the first non-empty line), then `# description:` (an authored text alternative), `# panels: syntax`, then `view:`.
- **Why:** One format everywhere. A fenced block cannot carry a data attribute, so options travel in the source.
- **Rejected:** A second embedding syntax; options as data attributes.
- **If wrong:** None.
- **Where:** Spec §6.5, §6.6, §10. `_includes/c4-view.html`, `js/ArchUML/c4/c4-render.js`, `js/uml-auto-describe.js`, `_plugins/uml_static.rb`. Tests: `scripts/tests/c4-content.test.js` (every include resolves), `scripts/tests/c4-description.test.js`.

### RR-2 Native ArchUML layout, no ELK

- **Date:** 2026-11-08 *(user; spec D6)*
- **Decision:** C4 views use ArchUML's own layout, synchronous once loaded.
- **Why:** The decision table states no reason. What the spec builds on it: synchronous static prerendering and description, layout shared with the other ArchUML renderers, and no new large dependency.
- **Rejected:** ELK.
- **If wrong:** Large; the routing redesign (RR-9) is the mitigation that was chosen instead.
- **Where:** Spec §6.4.

### RR-3 Supplementary views use UML

- **Date:** 2026-11-08 *(user; spec D5, D7)*
- **Decision:** The first release has context, container, component, dynamic, code, landscape, and deployment views. Code views are UML class diagrams, dynamic views UML sequence diagrams, deployment views UML deployment diagrams; the landscape stays in C4 notation. Every dynamic view's sequence text starts with `layout wrap 120` (2026-11-11, see AP-1).
- **Why:** The user asked for UML in the supplementary views; ArchUML already draws them.
- **Rejected:** C4 notation for dynamic views (numbered relationships). It remains a possible later decision; nothing depends on it.
- **If wrong:** A new dynamic-view notation.
- **Where:** Spec §6.3. `js/ArchUML/c4/c4-uml.js`. Tests: `js/ArchUML/tests/c4/uml.test.js`, `scripts/tests/c4-delegation.test.js`.

### RR-4 C4 drawing code is lazy-loadable, behind a bundle stub

- **Date:** 2026-11-08 (spec §17)
- **Decision:** C4 drawing code lives in `js/ArchUML/c4/c4-render.js` (with `c4-place.js` and `c4-route.js`), not in `uml-bundle.js`. Pages where C4 is the topic preload it; everywhere else a small stub in the bundle loads it on demand under a completion contract (one memoised promise, an accessible "Loading diagram" placeholder, description and fit after rendering, a visible error state and no retry loop).
- **Why:** SE Gym cards and other tutorials can show a C4 figure without paying for the toolkit on every page; two prerender caches and the tutorial bindings could not work as first written.
- **Rejected:** C4 drawing inside `uml-bundle.js`.
- **If wrong:** Moving code back into the bundle.
- **Where:** Spec §3.2, §3.3. Tests: `js/ArchUML/tests/c4/bundle-stub.test.js`, `scripts/tests/c4-lazy-render.test.js`.

### RR-5 A fixed palette baked into the SVG

- **Date:** 2026-11-08 (spec §6.2, §17)
- **Decision:** Diagram colours come from a fixed palette object, never from the CSS cascade. Light ArchUML-style tints with dark text replace C4's usual dark blue with white text; external elements are grey and also say "external". One exception since the polish round (2026-11-11): on screen in dark mode, the page's stylesheet gives a relationship label's backdrop (`data-c4-label-backdrop`) the colour the invert filter turns into the colour around the drawing (`--c4-label-backdrop`, `css/uml-diagram.css` and `css/c4-editor-theme.css`); the baked attribute stays white.
- **Why:** Static, live, exported, printed, and dark-mode renders bake identical values, and the site's dark-mode invert filter cannot double-invert them. The usual C4 blue reaches only 3.49:1. The backdrop exception: a baked white backdrop turns into a black patch behind every label on the dark page (final review M5), and no single baked colour matches both the light page and the inverted dark one.
- **Rejected:** Themed CSS variables.
- **If wrong:** Palette edits only.
- **Where:** Spec §6.2. `js/ArchUML/c4/c4-render.js`. Tests: `js/ArchUML/tests/c4/palette.test.js` (every colour on every backdrop), `tests/c4-display.spec.js` ("a relationship label sits on the page colour in light and dark mode").

### RR-6 Pins, label wrapping, and keywords

- **Date:** 2026-11-09
- **Decision:** A pin is a box's top-left corner, stored by view key, so a plain view and its annotated variant share pins; a box that grows into another moves the lower one down, and the view model marks it `pinAdjusted`. Since the polish round (2026-11-11), a pinned box keeps its pin and the box it overlaps makes room, above it or below it as the overlap lies (routing spec §4.7); only two overlapping pinned boxes move one of them, and the editor announces where a dropped element is drawn and what moved to make room. Every edge label wraps at the 300-unit box width. Element keywords are drawn as `«Container: Python, FastAPI»`, the stereotype convention of the other ArchUML renderers.
- **Why:** Spec §6.4 step 5 is normative; wrapping later would have moved coordinates other tests already asserted; one keyword style across ArchUML.
- **Rejected:** Pins keyed per annotation variant; wrapping only in interface views; `<<…>>` keywords.
- **If wrong:** A pin-code rewrite in one task.
- **Where:** Spec §6.1, §6.4. `js/ArchUML/c4/c4-render.js`, `c4-place.js`. Test: `scripts/tests/c4-layout.test.js`.

### RR-7 Every figure carries its source, safely escaped

- **Date:** 2026-11-08, confirmed 2026-11-09
- **Decision:** Every C4 container, live or static and including error states, holds a `<script type="application/json" data-c4-source>` with the source text. Every `<` is written as the six-character JSON escape `\u003c` (backslash, `u`, `0`, `0`, `3`, `c`), so `</script>` in a description cannot close the element; readers use `JSON.parse`.
- **Why:** The "Open in the C4 editor" link and the static/live comparison need the source; an unescaped `<` is an injection path. The escape was garbled several times in prose, so it is stated literally.
- **Rejected:** Reading the source from the fence text (gone after prerendering).
- **If wrong:** None.
- **Where:** Spec §6.5. `js/ArchUML/c4/c4-render.js`, `_plugins/uml_static.rb`. Tests: `scripts/tests/uml-static-plugin.test.js`, `scripts/tests/c4-interface-card.test.js`.

### RR-8 The static prerender accepts C4 HTML fragments, and static equals live

- **Date:** 2026-11-09; the SVG rewrite scope fixed 2026-11-11
- **Decision:** `uml_to_svg.js` returns the rendered C4 body (the card article, or the title, SVG, legend, and notes), and `uml_static.rb` accepts a fragment root. Its SVG-opening rewrite keeps a self-closing `/>` and touches only the SVG root, or every drawing only inside a C4 figure body. Static and live output are compared after removing the root's accessibility attributes: C4-notation views byte for byte, delegated UML views by node coordinates and route points. Card ids derive from the container id (else `c4-card-<interface id>`), not from render order.
- **Why:** Production and `static_uml` pages are prerendered; what a reader sees must not depend on which path drew it.
- **Rejected:** SVG-only prerender output; batch-order card ids.
- **If wrong:** Divergence between prerendered and live figures.
- **Where:** Routing spec §9.3 "How the checks compare and count". Tests: `scripts/tests/uml-static-plugin.test.js`, `tests/c4-display.spec.js`.

### RR-9 Routing redesign: a hybrid on shared primitives

- **Date:** 2026-11-09 *(user direction: "the routing has to fundamentally change … use the same kind of approach we use for component diagrams")*
- **Decision:** Option (c): two new axis-generic modules port the component renderer's ideas. `c4-place.js` re-ranks and orders to minimise crossings and assigns coordinates so edges run straight first, with room for every label; `c4-route.js` generates candidate routes per edge, filters illegal ones, picks a combination by deterministic global selection, spreads ports, and places each label beside its own route. The only bundle change is two entries in the C4 stub's script list, so component diagrams stay byte-identical by construction.
- **Why:** The first C4 router had avoidable bends, piled heads, and detached labels. The component router's ideas worked, but its code is one closure with order-dependent ties.
- **Rejected:** (a) extracting the component router into shared code (byte identity at risk, left-to-right only, reads the DOM width); (b) translating C4 views into component-engine input (no containment, sideways drawings). An earlier alignment-only fix was superseded.
- **If wrong:** About 2,000 lines of C4-only code to maintain.
- **Where:** Routing spec §0–§8. `js/ArchUML/c4/c4-place.js`, `c4-route.js`. Tests: `js/ArchUML/tests/c4/place.test.js`, `route.test.js`, `scripts/tests/c4-route-quality.test.js`, `scripts/tests/c4-route-metrics.test.js`; A/B tool `scripts/tools/c4-routing/ab-compare.js` (component corpus of 88 diagrams, live and static, three widths).

### RR-10 Objective order: conflicts and crossings before bends

- **Date:** 2026-11-09 *(on behalf of the user)*
- **Decision:** Spec §6.4 step 4a: within per-edge limits (at most two bends and no avoidable detour, with named exceptions), the router minimises, in order, conflicting ends, crossings, routes over arrowheads, close parallels, bends, then length. Zero avoidable bends is a gate. Crossings rank above close parallels.
- **Why:** The user's first direction asked to minimise bends; measured views showed that minimising bends first trades them for crossings and conflicts, which hurt reading more.
- **Rejected:** Bends first (the earlier §6.4 wording).
- **If wrong:** Re-ordering the objective and re-running every gate.
- **Where:** Spec §6.4, §17; routing spec §5.5, §11.

### RR-11 Thresholds are never loosened silently

- **Date:** 2026-11-09
- **Decision:** Gate thresholds are design targets from structural bounds. An implementer who shows one unattainable stops with evidence (an exhaustive search, a planarity argument, an infeasible constraint set, or measurements and images); thresholds may be tightened after measurement. Applied: the Booking API components view's crossing budget is 1, not 0, by a planarity proof; pinned views have no width cap; the 1,500 ms layout ceiling for the 40-element view was kept, and the code was made faster instead.
- **Why:** A gate that bends to fit the result stops being evidence.
- **Rejected:** Raising caps to match measured output.
- **If wrong:** None.
- **Where:** Routing spec §9.3, §9.4. Tests: `scripts/tests/c4-route-quality.test.js`.

### RR-12 Generated views that still fail become named ratchets

- **Date:** 2026-11-10, done 2026-11-11 (finalization ruling F1)
- **Decision:** Generated seeds 3, 4, 6, 8, 10 and the 40-element view each got one bounded, root-caused attempt. What still fails is a no-regression ratchet: the listed violations may shrink, never grow; no other violation may appear; every other gate runs in full; each test name states the structural reason.
- **Why:** Generated views are robustness probes, not learner-facing figures. An honest ratchet keeps the evidence and stops silent regression; a `todo` marker hid every other gate on those views.
- **Rejected:** Loosening thresholds; leaving `todo` markers.
- **If wrong:** A later task tightens the ratchets.
- **Where:** Routing spec §9.3 "Findings". `scripts/tests/c4-route-quality.test.js` (`GENERATED_RATCHETS`, `LARGE_VIEW_RATCHET`). See [Open items](#known-limitations-and-ratchets).

### RR-13 Boundary labels move; boundaries do not grow for them

- **Date:** 2026-11-09
- **Decision:** When a straight segment leaves through a boundary's label, the renderer slides the label along the bottom edge, else to the top-left inside. Boundaries are not widened for labels.
- **Why:** Widening a boundary moves every element inside it and breaks the straight-edge alignment.
- **Rejected:** Widening the boundary.
- **If wrong:** A label position rule.
- **Where:** Routing spec §4.1, §6. `js/ArchUML/c4/c4-render.js`.

### RR-14 Deployment labels are fixed in the UML deployment renderer

- **Date:** 2026-11-11
- **Decision:** Deployment views delegate to the UML deployment renderer, which placed each link label before later links existed and budgeted left-to-right gaps by label height. Labels are now placed after every route is drawn, clear of other routes, and left-to-right gaps are budgeted by label width.
- **Why:** On the chapter's production view two labels sat on the wrong arrows.
- **Rejected:** Passing only the technology on node-to-node links (less informative labels).
- **If wrong:** The fix changes 15 of the site's 16 deployment diagrams; they are about 20–25 % wider.
- **Where:** `js/ArchUML/uml-bundle.js` (deployment section). Test: `scripts/tests/c4-deployment-labels.test.js`.

### RR-15 One drawing for a dropped bend, and a faster orthogonal router

- **Date:** 2026-11-15 *(controller ruling on RR-11's threshold rule)*
- **Decision:** The timing gate of delegated UML views (250 ms median, 1500 ms ceiling) failed only on the reference model's `deployment production` with a stale bend: 544 ms, because the view was drawn, checked, and drawn again without the bend, and one drawing already took about 230 ms in the bundle's orthogonal connector router. The threshold was kept (RR-11). Instead:
  - the bundle gained the opt-in `UMLShared.renderSkippingDetachedRoutes(draw)`, inside which `applyLayoutRoutes` leaves out every stored route whose ends no longer lie on their boxes and returns their ids; `renderDelegatedView` draws once inside it (UML-view spec §6 rule 5 and §7.9, revision 3.2). The border rule (`pointLiesOnBoxBorder`, `storedRouteJoinsItsBoxes`, 1.5 units) moved from `c4-render.js` into the bundle, so it exists in one place;
  - the router got faster with the same output: `buildOrthogonalGraph` tests each grid point and segment only against the rectangles of its own lane, its node map is an `Int32Array` grid, and the A* search of `findOrthogonalGridPath` numbers its states and keeps them in typed arrays, with the same order, arithmetic, and tie rules.

  Result: the dropped-bend path 544 → 148 ms median, one drawing of the view 230 → 126 ms; the A/B guard showed 0 differences over the component, deployment, and C4 corpora, live and static, and 32 recorded drawings stayed byte-identical.
- **Why:** RR-11 forbids loosening a threshold silently; drawing twice was the cost, not the budget.
- **Rejected:** counting the second drawing against the ceiling only; a looser budget.
- **If wrong:** The opt-in is off by default; removing it restores two drawings.
- **Where:** UML-view spec §6, §7.9; routing spec §8. `js/ArchUML/uml-bundle.js`, `js/ArchUML/c4/c4-render.js`. Tests: `scripts/tests/c4-delegated-view.test.js`, `scripts/tests/timing/c4-delegated-view-timing.test.js`.

## Editor

### ED-1 Model-first with a live canvas; dragging by default

- **Date:** 2026-11-08 *(user; spec D4, §17)*
- **Decision:** An outline and inspector forms sit beside a navigable, editable diagram. Dragging is the default for moving, connecting, adding from the palette, refining from the carry-down tray, reordering, re-parenting, and panning. Single-pointer alternatives (context-menu commands, click-then-click, collapsed Position controls) and keyboard paths remain for WCAG 2.5.7 and 2.1.1 but stay out of the default view. Relationship details use a small anchored form, not a modal dialog; names are edited in place.
- **Why:** Undergraduates with little modelling experience expect direct manipulation; the alternatives keep it accessible.
- **Rejected:** A form-only editor; a canvas-first editor; modal relationship dialogs.
- **If wrong:** Large.
- **Where:** Spec §9.1, §9.2. `js/ArchUML/c4/editor/`. Tests: `tests/c4-editor-*.spec.js`.

### ED-2 The host contract

- **Date:** 2026-11-08; undo clarified 2026-11-09; callbacks 2026-11-10 (finalization ruling F5)
- **Decision:** The editor never touches storage, files, the network, cookies, the clipboard, `window.open`, or site globals; everything goes through the host object. There is one undo stack: on the site the editor owns undo and the Monaco YAML tab forwards undo and redo to it. Text equal to the editor's current text is a no-op (the echo rule). The editor routes Ctrl/Cmd+Enter to `onRequestCheck` and Ctrl/Cmd+S to `onRequestSave`, and tells the host when the learner chose Check now (`onCheckNow`) or Submit for review (`onSubmitForReview`).
- **Why:** The same editor must run on the site, in a tutorial, and in a future VS Code webview. Before F5 the tutorial adapter listened for keys itself and detected clicks on an internal attribute.
- **Rejected:** Two undo stacks; tutorial-side key and click detection.
- **If wrong:** Each host adapter changes.
- **Where:** Spec §3.4. [`docs/c4-editor.md`](c4-editor.md). `js/ArchUML/c4/editor/c4-editor-mount.js`, `c4-editor-panels.js`. Tests: `tests/c4-editor-contract.spec.js`, `scripts/tests/c4-editor-dom.test.js`.

### ED-3 The interactive layer is an overlay; the renderer stays unchanged

- **Date:** 2026-11-10
- **Decision:** The editor's accessible listbox is an overlay (`c4-editor-overlay.js`) attached to the SVG the normal renderer produces, using its existing hooks (`data-layout-id`, `data-c4-*`) and node boxes. Option targets carry `data-c4-option`, not `data-c4-target`, which already marks edge targets. The interfaces view gets a read-only listbox over its component nodes.
- **Why:** No edits to `c4-render.js` while the routing redesign was changing it; static output is unchanged by construction; the edge hook stays unambiguous.
- **Rejected:** An interactive mode inside `renderView`.
- **If wrong:** An interactive option added to the renderer later.
- **Where:** `js/ArchUML/c4/editor/c4-editor-overlay.js`, `c4-editor-canvas.js`. Tests: `scripts/tests/c4-interactive-render.test.js`, `tests/c4-editor-canvas.spec.js`.
- **Amended 2026-11-12 (UML-view editing; UML-view spec §7.1, §15):** the interactive layer stays an overlay, and the renderer gains one seam, `ArchUMLC4Render.renderDelegatedView(container, viewModel, options)`, which draws the layout-bearing `toUml` text of a UML-notation view inside the inner element, drops stale bends (RR-15), and returns `{ svgText, uml, droppedRoutes }`; `render`, the static prerender, and the canvas all draw through it, so the canvas no longer rewrites the document's `view:` line to make the renderer draw a UML view. The renderer no longer serves a read-only interfaces view: the overlay generalized into per-view option sets from a view registry (`c4-editor-uml-*.js` view modules), and an interfaces view is editable like the other three (UV-4, UV-12). The listbox group carries `data-layout-ignore`, so the bundle's route helpers skip it (`js/ArchUML/REFERENCE.md`, "Drawing over a rendered diagram").

### ED-4 One implementation per command, drag, and pointer path

- **Date:** 2026-11-09
- **Decision:** Element commands (delete with confirmation, rename, Move to…, Change id…) and the relationship-fields builder (with the read-aloud preview and the Uses picker) are implemented once in `c4-editor-actions.js` and called from the canvas, the outline, and the inspector. All canvas pointer input goes through one dispatcher; every drag (palette, outline, list rows, carry-down tray, canvas) is one drag session in `c4-editor-drag.js`. Quick fixes are an editor-side registry keyed by rule id, because the core's `fix` is `null` for every rule.
- **Why:** Duplicated form logic and competing listeners were the main risks of the largest unit.
- **Rejected:** Per-region implementations.
- **If wrong:** Small refactors.
- **Where:** `js/ArchUML/c4/editor/c4-editor-actions.js`, `c4-editor-drag.js`, `c4-editor-pointer.js`. Tests: `tests/c4-editor-actions.spec.js`, `tests/c4-editor-editing.spec.js`.
- **Amended 2026-11-12 (UML-view editing; UML-view spec §3.8, §15):** every drag is still one session on the one pointer dispatcher. Sessions for C4-notation views are built in `c4-editor-drag.js`; sessions for UML-notation drawings are built by the diagram editor's gesture factories (`session.gestures`), which the C4 canvas registers on the same dispatcher. The canvas and the forms share the actions of their kind (`renameElement`, `renameNode`, `renameInterface`, `deleteElement`, `deleteRelationship`, `moveRelationship`, `openRelationshipForm`), with a `wording: 'model-wide'` option for edits beyond the open view, and the rules they share live in the core (UV-8). The inspector's fragment guards, branches, and node links now go through core commands (`setFragmentOperator`, `setBranchGuard`, `addBranch`, `removeBranch`, `setNodeLink`, `removeNodeLink`) instead of its splice kit.

### ED-5 Moving a relationship is one core command, visible to novices

- **Date:** 2026-11-09; novice visibility 2026-11-09 (alignment decisions); chapter and tutorial text 2026-11-10 (ruling F4)
- **Decision:** A core command `moveRelationship` moves a relationship in one splice: a new target renames the collaborator key, a new source moves the entry, and the value text moves verbatim (description, choices, `responsibility`, `uses`). It refuses self-loops, containment links, and duplicates. The editor's "Move to…" command is shown in the novice profile, and the chapter's Practice and the C4 tutorial name it as the way to move a relationship.
- **Why:** Composing remove, add, and update lost fields, and refused relationships without a description, which novices often write. Delete-and-re-add loses the label and offers no keyboard benefit, since Move to… is a keyboard-operable button.
- **Rejected:** A `batch` of existing commands; delete and re-add in the learning materials.
- **If wrong:** None.
- **Where:** Spec §9.2. `js/ArchUML/c4/c4-edit.js` (`moveRelationship`). Tests: `js/ArchUML/tests/c4/edit-details.test.js`, `tests/c4-editor-editing.spec.js`.

### ED-6 Profiles filter diagnostics in the editor state

- **Date:** 2026-11-09
- **Decision:** The editor state calls `check` without `hideInfo`. The novice profile drops info diagnostics except `xlevel/unreceived` and `xlevel/unsent`, and suppresses incompleteness findings for elements and interfaces the learner has not touched yet.
- **Why:** Spec §7.2 excepts the two cross-level rules; the core's filter had no exception list. One owner for profile filtering.
- **Rejected:** Profile logic in the core.
- **If wrong:** None.
- **Where:** Spec §7.2, §9.3. `js/ArchUML/c4/editor/c4-editor-state.js`. Test: `js/ArchUML/tests/c4/editor-state.test.js`.

### ED-7 One lock semantics on both surfaces

- **Date:** 2026-11-09
- **Decision:** `locked_fields` paths are dotted; `*` matches exactly one key or list index; a lock covers the node and its descendants; there are no implicit exemptions. To lock an interface's syntax while its meanings stay editable, the author locks the syntax leaves with wildcards. One DOM-free `isLockedPath` serves the visual editor and the tutorial's YAML-surface revert.
- **Why:** A first ruling exempted semantic keys under `operations` and `types` implicitly; the plan review replaced it with explicit wildcards so an author can read what a lock covers.
- **Rejected:** Implicit semantic-key exemptions; separate lock code per surface.
- **If wrong:** Tutorial lock lists change.
- **Where:** Spec §11. `js/ArchUML/c4/editor/c4-editor-state.js` (`isLockedPath`, `lockedNodeOf`). Tests: `js/ArchUML/tests/c4/editor-state.test.js`, `scripts/tests/c4-tutorial-adapter.test.js`.

### ED-8 The "Open in the C4 editor" link is a site script

- **Date:** 2026-11-09
- **Decision:** A site script, `js/c4-editor-link.js`, adds the link over every `script[type="application/json"][data-c4-source]` figure, static or live, on pages that carry the editor meta. The renderer does not add it.

- **Rejected:** A link written by `c4-render.js`.
- **If wrong:** One extra file and include line.
- **Where:** Spec §3, §10. `js/c4-editor-link.js`. Test: `tests/c4-editor-standalone.spec.js`.

## UML-view editing

The four UML-notation views of the C4 editor (code, dynamic, deployment, interfaces) became editable by reusing the UML editor's interaction code (user request of 2026-11-12: "Allow the user to also modify the UML diagrams by reusing the UML editor code"). The design is [`docs/superpowers/specs/2026-11-12-c4-uml-view-editing.md`](superpowers/specs/2026-11-12-c4-uml-view-editing.md) ("UML-view spec" below), revision 3.2; the plan is `docs/superpowers/plans/2026-11-12-c4-uml-view-editing.md`. The user's decisions are U1 and U2 of 2026-11-12 and D1 to D7 of 2026-11-13 ([UV-16](#uv-16-the-users-answers-of-2026-11-13-uml-view-spec-14)).

### UV-1 One diagram-editor module with two edit adapters

- **Date:** 2026-11-12 *(user; UML-view spec U1, U2)*
- **Decision:** The UML editor's drawing interaction moved out of `_includes/uml-editor.html` into `js/ArchUML/diagram-editor/`, a framework-free, multi-instance module `ArchUMLDiagramEditor` whose parts register on `ArchUMLDiagramEditorParts` (its only two globals). It turns pointer and keyboard input on a rendered ArchUML drawing into *operations* and never writes anything itself. An *edit adapter* decides whether an operation is allowed and makes the change:
  - the **text adapter** (`diagram-editor/text/`): pure rewrites of ArchUML text, which keep the UML editor byte-identical to its behaviour before the move;
  - the **C4 model adapter** (`c4/editor/c4-editor-uml-adapter.js`, with one DOM-free planner per view in `c4-editor-uml-{code,dynamic,deployment,interfaces}.js` and the layout planner `c4-editor-uml-layout.js`): an operation becomes core commands dispatched as one `batch` (one splice, one undo step; SC-5), a shared editor action, a form, or a refusal with a sentence from the reviewed table (`c4-editor-uml-refusals.js`). It checks no model rule itself; it asks the core by a dry run.

  The module holds no copy of the document, keeps no undo history, and touches no storage, cookie, network, clipboard, or global beyond its two names. Dependencies point one way: site adapters → C4 editor → diagram editor → bundle; the C4 core does not depend on the diagram editor, and without its scripts a C4 canvas behaves as before.
- **Why:** U1 asks for a model-backed edit with `design.yml` as the single source of truth, and ED-4 asks for one implementation of every drag. Refusals then come before a change, in the model's own terms.
- **Rejected:** forms only (does not meet U2); parsing and comparing the generated text (cannot tell which model element was meant); embedding the UML editor (two sources of truth, two undo stacks); a second canvas editor for C4 (UML-view spec §2.5).
- **If wrong:** Large: both editors' canvases now run on the module.
- **Where:** UML-view spec §2, §3, §5. `js/ArchUML/diagram-editor/`, `js/ArchUML/c4/editor/c4-editor-uml-*.js`, `_includes/diagram-editor-scripts.html`. Tests: `tests/uml-editor-corpus.spec.js` (the sealed gesture corpus) and `scripts/uml-editor-gate.js` (the stage gate), `tests/diagram-editor-contract.spec.js`, `js/ArchUML/tests/diagram-editor/`, `js/ArchUML/tests/c4/uml-{adapter,layout-planner,planner-*,refusals}.test.js`.

### UV-2 The layout of UML-notation views: named parts, and what cannot hold a place

- **Date:** 2026-11-12; positions of interfaces views 2026-11-13 *(user, D3; see UV-12)*; deployment positions of top-level nodes only *(user, D4)*
- **Decision:** A layout entry under a UML-notation view key has named parts (main spec §4.8): `positions` (code and interfaces views: every drawn box; deployment views: top-level nodes only), `routes` (code and deployment views: `{from, to, relation, points}`, a hosted instance written `<element>@<node>`), and `lifelines` (dynamic views). `toUml` writes the entry into the text as ArchUML's own layout block, so the canvas, embedded figures, the static prerender, print, and "Copy ArchUML source" draw one picture. The first move pins every box that can hold a position; an addition goes to the drop point or a free place and is pinned; "Reset layout" removes the view's entry. A UML box with a position moves alone; its neighbours do not make room. Overlaps are never silent: after every drawing of a view that holds positions, one check names the first new overlapping pair and offers "Move ‹Name› to a free place". A stored bend lasts as long as its line still joins its two boxes (rule 5 of UML-view spec §6; RR-15). What cannot hold a place is refused with a reason: `layout/inside-node`, `layout/inheritance-line`, `layout/parallel-lines`, `layout/assembly`, `layout/port`.
- **Why:** Probes of the bundle: a pinned nested deployment node is drawn outside its parent; generalization and realization lines carry no route id; relationship ids of parallel lines are positional; the parts of a ball-and-socket line are numbered in drawing order, which changes when a box moves. Named parts, because `routes` and `lifelines` are legal element ids and a reserved key beside them could collide.
- **Rejected:** more keys in the flat pin map; a `participants` list on the scenario (lifeline order is presentation); positions of nested nodes (D4).
- **If wrong:** Medium. Lifting a limit is a bundle change and one refusal less (UML-view spec §2.6).
- **Where:** Main spec §4.8; UML-view spec §4.2, §6. `js/ArchUML/c4/c4-edit-sections.js` (`setUmlLayout`), `c4-uml.js`, `c4-model.js`, `c4/schema/1/design.schema.json`, `c4/editor/c4-editor-uml-layout.js`. Tests: `js/ArchUML/tests/c4/layout-uml.test.js`, `uml-layout-planner.test.js`, `scripts/tests/c4-delegated-view.test.js`, `scripts/tests/uml-static-plugin.test.js` (static equals live with pinned fixtures).

### UV-3 No declare shortcut from a refusal

- **Date:** 2026-11-12; confirmed 2026-11-13 *(user, D2)*
- **Decision:** A refused step in a dynamic view gives novices no offer to declare a relationship. A reply may offer "Add the request … first…". The expert profile gets "Declare a relationship …" behind the relationship form, which asks the structural question first. The offer carries an `operation`, not `commands`, so the canvas never declares a relationship in one click.

### UV-6 When the document is read

- **Date:** 2026-11-12 (plan Global Constraints; refines UML-view spec §2.1)

### UV-12 `layout ports facing` and the positions of an interfaces view

- **Date:** 2026-11-13 *(user, D3)*; built 2026-11-13 (Task 2b) and 2026-11-21 (Task 46)
- **Decision:** The boxes of an interfaces view can be moved and hold `positions`, like a code view. The bundle's component renderer gained the directive `layout ports facing`, read on a line of its own before the shared layout directives: when the document gives at least one component a saved position, the sides of every joined ball and socket are chosen after the positions are applied, to face the partner (below, above, beside; the larger gap when apart in both directions, the diagram's direction on equal gaps; overlapping or touching boxes keep the automatic sides; a port in several assemblies faces the partner of its first). A port with its own saved position, a port outside every assembly, and a plain port keep their sides. A box keeps its top-left corner on its position and may change size. Where two boxes beside each other share a height at which both can hold a port, the line is straight; where they overlap only outside such heights it bends once in the gap (decision 11 of Task 2b). Without a saved component position, and without the directive, every drawing is byte for byte as before (A/B: 0 differences over 89 component, 16 deployment, and 72 C4 sources, live and static). `toUml` writes the directive only into an interfaces view whose entry gives a drawn box a position, and the UML editor never writes it; its layout control and write-back leave the line alone. The legend names the subject: "… The subject of this view is ‹name›." in the figure, in `describe`, and in the editor; "consumers above, the element in the middle, providers below" is the automatic layout only. The line between a ball and its socket holds no bend and a ball or socket no position (`layout/assembly`, `layout/port`; one of the two points §14 decided for the user, see UV-16).
- **Why:** A moved consumer kept its socket on the far side, and its line ran around both boxes (probe); a place cannot identify the subject once boxes move, and pointing at a place says nothing to a reader who does not see the layout (WCAG 1.3.3).
- **Rejected:** keeping interfaces views without positions (`layout/fixed-order`, revision 2); changing the sides of every component diagram (would change the 89 site diagrams).
- **If wrong:** The directive is opt-in; removing it restores today's drawing everywhere.
- **Where:** UML-view spec §5.5, §6; main spec §6.6. `js/ArchUML/uml-bundle.js` (component renderer: `facingPortPlan`, `sideFacing`, `alignFacingStackPorts`), `c4/c4-uml.js`, `c4/c4-describe.js`, `c4/editor/c4-editor-uml-interfaces.js`; `js/ArchUML/REFERENCE.md` ("Balls and Sockets That Face Their Partners").
