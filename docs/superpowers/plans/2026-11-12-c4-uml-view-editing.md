# C4 UML-View Editing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the UML editor's drawing interaction into a reusable, multi-instance ArchUML module with edit adapters, keep the UML editor byte-identical through a text adapter while it moves, give it moves without a drag afterwards, and make the C4 editor's four UML-notation views (code, deployment, dynamic, interfaces) editable through a C4 model adapter that writes `design.yml` or refuses with a visible reason.

**Architecture:** Seven behaviour-preserving stages (R0–R6, Tasks 1–25) take the drawing code out of `_includes/uml-editor.html` into `js/ArchUML/diagram-editor/` and its ArchUML grammar knowledge into a pure text adapter. Each stage is guarded by the existing UML editor suites, a sealed byte-identity gesture corpus, computed-style evidence, and the stage's audits. In parallel the C4 core gains projection fields, `toUml` ids and source maps, keyword-safe aliases, UML-view layout parts, shared constraints, and commands (Tasks 26–30). The C4 editor then mounts the module under its own listbox, keys, message region, and undo stack, with one DOM-free planner per view (Tasks 31–46). Tasks 47–48 update tutorials, documents, and run the release gate. Two bundle changes come first, in Lane R, before the corpus is recorded: the `data-layout-ignore` skip (Task 2) and the component renderer's opt-in `layout ports facing` (Task 2b), which lets an interfaces view hold positions. After R6, stage A1 (Tasks 25b and 25c) gives the module moves without a drag and the UML editor its ways into them: the editor's one behaviour change. The work runs in waves: lanes work concurrently and check themselves, and one gate agent runs the conclusive commands alone at each wave boundary (Waves).

**Tech Stack:** Plain JavaScript UMD scripts (no build step, no `import`/`export`, no AMD branch), Liquid includes, CSS custom properties, Node 22 `node:test`, Playwright with Chromium (`@playwright/test`, and `playwright` inside `node:test` renderer tests), `@axe-core/playwright` through `tests/a11y-helpers.js`, `@babel/parser` for source-structure tests, Jekyll.

**Spec:** `docs/superpowers/specs/2026-11-12-c4-uml-view-editing.md` (revision 3.1). Its binding context travels with it: `docs/superpowers/specs/2026-11-08-c4-model-design.md` ("C4 spec"), `docs/superpowers/specs/2026-11-09-c4-routing-redesign.md`, `docs/c4-decisions.md`, `docs/c4-editor.md`, `CLAUDE.md`. - **When the document is read.** The session reads `adapter.contents()` once per `sync`, and the scene uses that reading for hit testing. A command reads `adapter.contents()` again when it builds an operation and resolves every reference (a route's line, an anchor, a member) against that reading; the operation carries that reading's revision. For the text adapter this is today's behaviour: the canvas parses the textarea at gesture time, also inside the 120 ms debounce after typing, when ordinal route ids (`edge-N`, `usecase:N`) are matched against the current text. For the C4 adapter both readings come from the drawing, and `apply` refuses a changed document with `stale`. This refines spec §2.1; Task 48 records it.
- Revision token, shared by both adapters so a logged operation replays in another process: `revisionOf(text)` = `'r'` + the FNV-1a 32-bit hash of the text's UTF-16 code units in lowercase hex + `':'` + `text.length`.
- C4 edits reach the document only through `state.dispatch` as one `batch` per gesture (one splice, one undo step; SC-5), honouring C4 spec §4.9: bytes outside the edit ranges unchanged, add-then-delete identity, refused while the YAML has errors. Shared editor actions are called, never re-implemented (ED-4): `actions.renameElement`, `actions.deleteElement`, `actions.deleteRelationship`, `actions.moveRelationship`, `actions.openRelationshipForm`. Task 35 gives them what the canvas needs (a `wording: 'model-wide'` option; per-kind placeholders and UML-view layout sites in the first-rename id rule) and adds `actions.renameNode(environmentId, nodeId, name)` and `actions.renameInterface(interfaceId, name, { wording })`, which the Name fields of the node form and the interface form call too. A shared action announces its own result or refusal, so the verdict of an `action` plan has `message: null`, and the module announces only a verdict that has a message: each change is announced once. The adapter checks no model rule itself; it asks the core by a dry run.
- **Identity (spec §5.1, §14 D1).** An id follows only the first rename of a thing that still has its placeholder name and id: an element, a deployment node, or an interface. Every rename goes through the shared action of its kind, from a canvas and from a form alike, so the rule has one implementation for each kind.

## Parallel lanes

All lanes work in the one working tree of each repository (PR-2): no worktrees. A lane writes only its own files (`lanes.json`, Task 0). Lanes run in **waves** (Waves): the lanes of a wave work concurrently, and when each has passed the `CHECKPOINT` of its last task in the wave, one gate agent runs the conclusive commands alone. A lane agent cannot ask the controller for anything while a wave runs, so there are no QUIET windows (controller ruling, 2026-11-13).

The lanes are disjoint in files, not in what their commands execute. `UNIT`, `BUILD`, `GATE`, the site audits, `TIMING`, and every harness spec that loads a manifest run other lanes' files as they are on disk, and every task leaves red tests in the tree between its red run and its checkpoint. So:

- **During a task** a lane checks itself with `UNIT-TASK` and with its own specs. Those results are indicative.
- **One lane of each wave is its builder.** It alone runs `BUILD` and specs that load built pages, under the site lock, in steps marked `IN-LANE`.
  - Lane R is the builder of waves 0 to 3 and runs its stage gates itself. Their subject is the UML editor, which loads no file of Lane K or Lane C, and those lanes build nothing while Lane R works. An in-lane run that fails in a C4 file or a C4 figure is run again after that lane's next checkpoint (a new `lane-<lane>/last.json`); if it still fails, the lane notes it for the wave gate and goes on.
  - Lane C is the builder of wave 4, where it is alone.
  - Lane V-dyn is the builder of wave 5. Its built-page runs there are indicative, because the tutorial page also loads the files of the other two V lanes.
- **Every other conclusive check is deferred** in a step marked `DEFER`: the task records it, and the gate of the wave runs it. A step that read "QUIET: … → PASS" in plan revision 2 is now `IN-LANE`, `DEFER`, or both.
- **Rulings come in two kinds** (PR-3). The gate report lists every open ruling, and the controller answers them before the next wave starts.
  - **A ruling that does not block the task** is recorded as pending in the task's own files, the task passes its `CHECKPOINT`, and the lane goes on. The lane's first task of the next wave applies the answer before anything else. Task 10's unreached write sites are of this kind (`ruling: 'pending'`; Task 11 Step 0 applies the answers).
  - **A ruling that blocks the task** stops the lane: a file outside its write set, a computed-style difference that comes from the cascade (Task 24), or a gate failure the accepted-change rule does not cover (Task 25c). Nothing is undone, because PR-1 forbids reset and stash. The lane writes under "Needs ruling" in its lane note the question, the stopped task's files as they are, and their failing tests, and ends its run.
  - **The gate and a stopped lane.** The gate still runs every command. It lists each failure it attributes to the stopped lane under "pending ruling", and those failures neither pass nor fail the wave. After the ruling the controller resumes the lane at the stopped task, the lane finishes its tasks of the wave, and the gate runs again in full. The next wave starts only after that full run is green.
- **A finding for another lane's file** (a wording in the reviewed refusal table, say) does not stop a lane. It goes under "For the gate" in the lane note, and the controller assigns it.

### Wave gates

The gate agent works alone. No lane agent runs, and every lane of the wave has passed the `CHECKPOINT` of its last task in the wave or stopped for a blocking ruling, as its lane note says.

0. It compares each repository's branch and HEAD (`git branch --show-current`, `git rev-parse HEAD`) with `confirmedHeads` in `lanes.json` (Task 0 Step 0). If either moved, it writes what moved (`git reflog -5`) into `gate-<w>.md`, runs nothing else, and judges nothing; the controller asks the user before any lane or gate runs again.
1. It runs `UNIT`, then `BUILD`, then the wave's gate commands (Waves), then every command the wave's tasks deferred (`lane-<lane>/deferred.json`), each once, with `JEKYLL_PORT=4410`, holding the site lock.
2. It judges each result against gate 0. A test that fails and failed at gate 0 is reported by name (PR-5). A test that fails and passed at gate 0, or did not exist then, fails the gate.
3. It attributes each failure: to the lane whose write set holds the failing test or the file the failure names; and when the test lies in another lane's area, to the lane whose checkpoints changed a file the test loads since the last green gate (`lane-<lane>/task-<n>.json` hold the hashes after each task).
4. It writes `gate-<w>.md` (ignored by git): each command with its result, the known failures by name, the attributions, the open rulings, and the findings lanes left "For the gate". It changes no file of either repository.
5. On a red gate the attributed lane repairs within its write set (a red run of the failing test first, then the fix, then its `CHECKPOINT`), and the gate runs again in full. Failures attributed to a lane stopped for a blocking ruling are listed under "pending ruling" and wait for that lane (Parallel lanes). The next wave starts only after a green gate and after the controller has answered the open rulings.

## Commands the tasks use

- `E` — `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8`.
- `IN-LANE: <commands>` — the wave's builder lane runs them itself, holding the site lock. For Lane R (waves 0 to 3) and Lane C (wave 4) the result decides the step. For Lane V-dyn (wave 5) it is indicative. The wave gate runs the same commands again.
- `DEFER: <commands>` — the lane does not run them conclusively. It appends `{ task, command, expects }` for each to `lane-<lane>/deferred.json`, and the wave gate runs them. A lane may run a deferred command that needs no build (`UNIT`, `C4-HARNESS`, a `PW` spec) as an indicative check.
- **Site lock.** `_site` is shared. The wave's builder and the gate agent hold the directory lock `"${TMPDIR:-/tmp}/sebook-site.lock"` (taken with `mkdir`, which fails while another holds it; wait for it with a condition loop, never a fixed sleep; remove it with `rmdir`) for the whole of each `BUILD` and of each Playwright run that loads site pages. Specs that build their page with `page.setContent` and load scripts from disk need neither a build nor the lock.
- `PW <files>` — `E PLAYWRIGHT_SERVE_BUILT_SITE=1 JEKYLL_PORT=<lane port> npx playwright test <files>`, for `setContent` specs.
- `PW-SITE <files>` — under the lock, after `BUILD`: `PW <files>`, for specs that load built pages. Only the wave's builder and the gate agent run it.
- `UNIT-TASK <files>` — `E node --test <files>`: the task's own unit tests and the pre-existing ones it names. Indicative.
- `UNIT` — `E npm run test:unit` → no failure that gate 0 did not record. Conclusive at a wave gate, and in a lane that is alone in its wave (Lane R in wave 3, Lane C in wave 4).
- `BUILD` — under the lock: `E bundle exec jekyll build`. Needed before a site-page run whenever a file the build copies changed (includes, layouts, pages, `css/`, `js/`). Only the wave's builder and the gate agent build.
- `GATE` — under the lock, after `BUILD`: `E PLAYWRIGHT_SERVE_BUILT_SITE=1 JEKYLL_PORT=<port> node scripts/uml-editor-gate.js --baseline .superpowers/sdd/2026-11-12-c4-uml-editing/gate-baseline.json` → exit 0, last line `gate: <n> files, 0 changed since R0, <k> accepted, evidence <sealed and unchanged | not sealed yet>, 0 new failures`. `<k>` is 0 until Task 25c.
