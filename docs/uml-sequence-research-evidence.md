# Evidence for sequence inference hardening

Research date: 19 October 2026. This is a focused engineering review, not an exhaustive systematic review or a claim that the implementation reproduces these research systems.

The question is how to improve the existing browser-local static inference for Python, Java, C++, and TypeScript while preserving its interactive latency and existing behavior. Relevant work concerns reverse engineering interactions, receiver identity, call-target resolution, control flow, and analysis bounds. Dynamic extraction is included to understand its guarantees and limitations; executing student code or adopting a different analysis architecture is outside this change's scope.

## How the evidence was collected

The `lit-search` workflow supplied the search, screening, snowballing, and annotation structure. Sider Scholar supplied OpenAlex discovery and identifier lookup. SciSpace was used separately for sequence-extraction research discovery. Technical claims below rely on papers or official specifications, rather than generated connector summaries. There was no publication-year cutoff. English-language papers with a concrete connection to the engineering question were preferred; patents, unrelated NLP/image diagram generation, and keyword collisions were excluded.

Sider's `search_open_access_works` returned compact title/author/link records. Its `get_open_access_work` response also omitted abstracts and reference arrays, despite the advertised complete-record interface. Consequently, abstracts and relevant full-text sections were obtained from author, university, publisher, or arXiv pages. Counts below describe returned records, not the total literature. Empty results do not establish absence of research.

**Backward snowball:** the references in Rountev and Connell's object-naming paper identify Rountev, Kagan, and Gibas's call-chain analysis, Tonella and Potrich's C++ interaction extraction, and the earlier control-flow technical report. Their bibliographic records were checked separately. **Forward snowball:** both OpenAlex citation filters above found StaticGen, connecting the earlier object-identity and scenario-extraction work to later static sequence generation. These were one-hop, relevance-screened expansions, not an exhaustive citation closure.

The Carleton repository PDF endpoint failed to fetch through the web reader. The full OMG UML PDF exceeded that reader's size limit. Some publisher/DOI redirects failed, so author copies and institution-hosted papers were used where available. No paywall was bypassed. One mistyped DOI returned an unrelated software-patents keynote; it was excluded and the JavaScript paper's DOI was verified from DBLP and its author publication page.

SciSpace's semantic query was: “What static, dynamic, and hybrid program analysis approaches recover accurate UML sequence diagrams from object-oriented source code, and how do they handle polymorphism, aliasing, recursion, conditional control flow, and asynchronous calls?” It returned ten records. Two patents were excluded; the 2017 StaticGen proceedings paper and its expanded journal paper were treated as one research line. A `limitations` extraction for StaticGen, Rountev's control-flow paper, Labiche's hybrid approach, and Ziadi's dynamic approach guided follow-up reading. Generated extractions were not used as independent evidence for unavailable full texts. Baidada's hybrid approach, Ziadi's dynamic approach, JRET, and the UML2 static/dynamic combination were background candidates rather than justification for changing the execution model.

## Engineering implications

Official semantics provide the oracle for the implementation fixes. [Java Language Specification §14.20.2](https://docs.oracle.com/javase/specs/jls/se25/html/jls-14.html#jls-14.20.2) distinguishes normal and abrupt completion and specifies the effect of `finally`, including replacement of an earlier completion reason. [ECMAScript conditional and logical-expression semantics](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-conditional-operator) specify conditional operand evaluation. These sources were read independently of the scholarly connector summaries.

These are project recommendations derived from the evidence, not claims that the papers validate the implementation:

1. **Make uncertainty part of the analysis result.** Keep structured warning categories and source context through rendering/export. Distinguish unsupported syntax, unresolved receivers, ambiguous dispatch, deferred execution, and resource bounds. A rendered diagram is not evidence of complete inference.
2. **Keep path state separate.** Analyze alternatives from the same incoming state, then merge only their reachable exits. Retain a definite receiver when all relevant paths agree; otherwise warn or retain alternatives. Do not let traversal order choose the receiver after an `if`.
3. **Track completion explicitly.** Normal fall-through, return, throw, break, and continue differ. A return terminates its method path; a break terminates the corresponding loop/switch path. An unmodeled exception path needs a warning rather than a fabricated normal return.
4. **Separate identity from display labels.** Aliases and actual/formal/return bindings should preserve known object identity. Reassignment, repeated allocation, and collections require an explicit abstraction; variable spelling is insufficient.
5. **Bound work, not just call depth.** Guard expression traversal, statement visits, emitted interactions, and active recursive expansion. Detect cycles on the current expansion stack, so independent repeated calls are not mistaken for recursion. A recursion warning must not assert that every recursive program loops forever.
6. **Respect language evaluation and scheduling rules.** Calls in receivers, arguments, conditions, constructor initialization, and return expressions can produce interactions. Short-circuit operands and deferred callbacks/generators cannot be flattened into unconditional immediate calls. Use official language specifications as the oracle for ordering; the call-graph papers do not supply it.
7. **Use discriminating regressions.** Pair positive cases with nearby counterexamples: aliases versus distinct instances; two ordinary calls versus active recursion; one terminating branch versus two; empty constructors versus initializer effects; callback creation versus invocation. Retain published examples and tutorial grading tests, and test warnings clearing after correction.

Full path enumeration, solver-backed feasibility, whole-program points-to analysis, and actual execution are larger architectural choices. They can improve particular guarantees, but are not required to address the concrete silent failures above. Their adoption would need an explicit decision about latency, dependencies, scope, and what the diagram promises.
