# Local Python specification assistant

The optional add-on generates Python from a student's natural-language specification and runs conceptual checks through the existing Python tutorial backend. Its current target is Qwen2.5-Coder 3B Instruct with four-bit quantization, running locally. The demonstration is `/SEBook/tools/python-specification-tutorial`, with a matching `/print` page.

The 3B target follows the request for less RAM use than the 7B option. Downloaded weight bytes, peak runtime memory, and generation quality are separate measurements: a smaller download does not establish that a browser fits a particular device. The historical 1.5B results below do not validate the 3B target; real 3B inference results are recorded separately below, and peak memory remains unmeasured.

## Authoring

Enable `llm: true` on a Python-only `backend: pyodide` tutorial. Mixed backends are not supported.

Set top-level `ai_tutor: true` to enable the optional chat inside the model panel. It shares the selected engine, downloaded model, loading and cancellation controls. No second model is downloaded. The Python specification demo and Warehouse Rover enable it. Authored failure hints remain independent.

For code-comprehension exercises, set `ai_tutor_mode: source` at tutorial or step level. Warehouse Rover uses this mode: the model selects a coaching move, function and focus as JSON; `source-coach.mjs` turns the selection into an authored natural-language question. The existing Python AST service verifies functions and statement locations without executing the source. Model explanations, specification clauses and arbitrary extra fields are rejected. An unusable focus falls back to a question about the verified function, without asserting a nonexistent statement. Repeated questions change to a contrasting-input challenge, then offer a smaller task or human help. Prerequisite moves offer verified course links. This constrains factual claims; it does not prove that the model chose a useful question or assessed understanding correctly.

Set `ai_tutor_mode: independent` on transfer steps to allow only general reflection, prerequisite resources and stopping. Source hints and diagrams are rejected. Omitted mode preserves the general natural-language coach used by the small Python demo; its answer boundaries are prompt-based and weaker. The mode is passed through the layout and tutorial constructor separately from step guidance:

```yaml
ai_tutor: true
ai_tutor_mode: source
steps:
  - title: Read the program
    ai_tutor_instructions: |
      Ask for a prediction and source evidence. Do not write a specification.
    files:
      - path: main.py
        content: "# Supplied source"
  - title: Independent transfer
    ai_tutor_mode: independent
    ai_tutor_instructions: |
      Offer only general reading strategies and prerequisite resources.
```

Every turn includes complete step guidance, public interface, learner specification and **all current workspace files**, using live editor values where available. Hidden checks, grading metadata and instructor solutions are excluded. These inputs never enter the separate specification-generation or feedback prompts. Successful dialogue turns stay complete in memory; there is no automatic clipping or model-written summary. Steps reset the chat. **Start fresh context** cancels pending work and clears model history while retaining the visible transcript and unsent draft; it invites a learner-written recap. Current source and guidance are still sent. **Reset chat** also clears the transcript and draft. Neither changes model downloads or tutorial work.

The 2,048-token context and ONNX's 768-token input ceiling still apply. Exact native input rejection preserves the draft and successful history, and a recognized rejection before output retains the loaded runtime. No shortened retry or engine switch occurs. wllama uses `ctx_shift: false`. Output/context exhaustion marked `length` discards the partial reply. A fresh conversation whose source already exceeds an engine's limit must use another compatible engine or human/lesson support; resetting cannot make that source fit. A rough character counter is not presented as an exact token meter.

`runTutorTurn` makes one coaching generation (up to 192 tokens). A diagram is a bounded tool request: a single fenced `tutor-tool` or `json` object with exactly `tool: draw_diagram`, `type` and a `focus` of at most 240 characters. A second generation (up to 384 tokens) receives one relevant ArchUML grammar, full public context and the request. There is no recursion, execution tool or automatic repair loop. Syntax examples were removed from the coaching prompt because the real small model copied them into unrelated replies.

In source mode, the current learner message must request a visual, and a learner message must identify one direct call (for example, “navigate calls process_command”). Python AST analysis verifies that direct call between uniquely named functions in the same file. Only a sequence diagram with those two participant labels and one arrow labeled `calls` is accepted; extra participants, relationships and diagram statements are rejected; aliases and arrow labels are replaced with verified names and the fixed label `calls`. The learner-facing question about that verified relationship survives an unavailable drawing. This deliberately limits source-mode diagrams to small call maps. General mode supports class, sequence, state, activity, component, deployment and use-case drawings; syntax validation there is not semantic validation.

The existing renderer uses a disposable worker, sanitized SVG, paragraph-size labels, structural text alternatives and keyboard scrolling. Its source disclosure remains available. Generic UML fences and bare complete UML are recognized, but unsupported code fences are never executed. Stop/reset/navigation discard late generation and rendering. A failed optional drawing retains the coaching question and a recovery notice. See [the local tutor evaluation](local-tutor-evaluation.md) for observed model failures, rehearsal results and limits.

Each participating specification-assistant step declares:

```yaml
llm:
  file: solution.py
  interface: "Define unique_in_order(items). Accept a list of integers and return a list."
  specification: "Remove repeated integers."
  checks:
    - category: ordering
      command: "assert subject['unique_in_order']([3, -1, 3]) == [3, -1]"
```

The destination must be an editable file. Keep the public interface within 600 characters and editable specification within 1,200. Describe the intended behavior in the lesson so the student can reason about it; hidden checks must not introduce unstated requirements. At most 20 check groups run in a bounded Python worker transaction. Each command receives `subject`, a fresh namespace containing the current program. Allowed categories: `ordering`, `duplicates`, `boundaries`, `input-contract`, `output-contract`, `mutation`. Use independent checks and review plausible wrong implementations. Hidden check commands stay out of prompts, normal results, and print output; browser developer tools can inspect the authored data.

For exercises where students read an original program and work only on prose, set `llm.mode: specification` and point `llm.file` at the supplied original. **Test my work** generates a private candidate and immediately runs the same authored checks against it; it never replaces a workspace file. An optional **View generated Python** disclosure shows the exact completed candidate in a read-only, syntax-highlighted code region. The shared Python highlighter builds inert text nodes and spans; model output is never inserted as HTML. The region is keyboard focusable, works in both themes, and is cleared on edits, cancellation, navigation, or another check. Only the public interface and submitted prose reach the model. The specification field and Test my work button appear before the step instructions. A downloaded model is needed for this action. Set the same optional `llm.draft_id` on related steps to carry one session draft between them; omit it to keep separate per-step drafts. The helper contract can use its own draft ID. Cancellation, prose edits, file edits, and navigation discard stale work. Feedback uses fixed conceptual questions and never reveals hidden cases. Generated source appears only in its separate optional inspection view. Model failures are distinct from evidence of an incomplete specification; do not gate lesson progress on successful generation. The six-stage example is `/SEBook/development_practices/code-specification-tutorial`, with a 108-line rover original, persistent prose notes, and an independent transfer exercise.

Both generation workflows request a complete, self-contained Python file, including every helper and constant. `program-generation.mjs` allows up to 1,024 output tokens and calls `python-completeness.mjs` through the existing Python worker before enabling application or behavioral checking. This source-only inspection compiles the candidate and uses Python's symbol tables to identify unresolved global names, including references inside helpers. It also rejects static imports of tutorial files and non-standard-library dependencies. It never executes the candidate, reads workspace files, or receives hidden checks. Parameters, closures, recursion, builtins, and explicit standard-library aliases remain valid. This is a structural check; dynamic lookup, attribute existence, initialization order, and behavioral correctness still require execution tests.

An incomplete/truncated or syntactically invalid response gets at most one full regeneration. The retry receives only the public interface, student prose, and source-derived missing names/imports; it gets no hidden test details or original program. A remaining incomplete candidate cannot be applied or proceed to behavioral checks. The optional inspection view can still show the failed final attempt, with failure feedback. Cancellation and edits invalidate both attempts. Ordinary behavior mismatches do not trigger regeneration.

Prose-check status distinguishes **Checks passed**, **Did not pass** (incomplete file, behavior mismatch, syntax error, or runtime error), and **Not checked** (unfinished generation or unavailable checks). The candidate namespace cannot borrow helpers from the original or earlier runs. Editing prose/files or changing steps clears the previous check announcement as well as its feedback. Moving to another mission is independent of passing a generated-program check.

The interface starts with the editable specification and an expandable public function contract. It shows one primary action at a time: Download model (with the size visible before download) or Generate Python (Test my work in prose-only mode). Cached models load automatically when generation or conceptual feedback needs them; there is no separate load button. A spinner and live status describe preparation, with Cancel available. The spinner stops animating under reduced motion. If cached data has been evicted, automatic loading stops and offers an explicit download instead of fetching weights. Downloading shows byte and percentage progress with Cancel. Model & storage expands to reveal engine selection, device details, comparison, unload, and deletion. These controls remain available on steps without an exercise.

Check Python works without a model. It checks the current editor contents and reports only conceptual mismatches, syntax/runtime trouble, or unavailable checks. If a model is already downloaded, it loads when needed to suggest questions from the public prose and failed categories. Passing checks and syntax/runtime errors need no model initialization. It never receives hidden test source, input/output values, or exception text. Its suggestions may be wrong; failed code is not proof of a faulty specification. Passing checks is not proof of completeness. Generated Python is previewed, applied only by a separate action, and checked through Python only. Edits/navigation invalidate stale suggestions and cancel in-flight work. Feedback appears below the actions only when there is something to report.

## Engines and selection

- WebLLM 0.2.87: WebGPU, MLC `q4f16_1`, **1,743,386,562 model bytes** including metadata/tokenizer, pinned at revision `5213029e7ae2ad46baf9657aa491186e56cd34d6`.
- wllama 3.8.1: WebGPU or WebAssembly processor inference, GGUF `Q4_K_M`, **2,104,932,800 bytes**, pinned at revision `f74adce6aa16316c625447af059dbebe4983757c`. Hosted compatibility assets cover browsers lacking newer WebAssembly features.
- Transformers.js 3.8.1 with ONNX Runtime Web 1.22.0-dev.20250409-89f8206ba4: JavaScript WebGPU backend, ONNX `q4f16`, **2,379,064,640 bytes** including tokenizer/configuration, pinned at revision `0e076a9c5291f8c74b3ce1558f21336b18f94739`. The graph is 271,268,174 bytes and its external weights are 2,096,365,568 bytes. This is the Firefox graphics path.
- All three derive from the same upstream Qwen2.5-Coder **3B Instruct** checkpoint. Quantization/layout differ, so their generated outputs need not be identical. The byte counts describe downloads, not peak RAM.
- Context: 2,048 tokens; output: up to 1,024 tokens for either code-generation workflow and 220 for feedback. ONNX retains the conservative 768-token cap on the complete templated input: its graph materializes FP32 logits for every prompt position. Longer inputs are rejected before graphics execution with a request to shorten the specification or choose Processor; input is never silently truncated. One worker/model and one request at a time. Processor threads are capped at four and half the reported concurrency, or one without isolation.

Preflight requires nine storage buffers for ONNX, half precision, **1 GiB for both `maxBufferSize` and `maxStorageBufferBindingSize`** (the 3B embedding table is about 622 MB), and 32 KiB workgroup storage. WebLLM requires ten storage buffers per shader stage, half precision, and the same 1 GiB buffer/binding limits: the pinned runtime otherwise falls back to a 128 MiB binding, too small for a roughly 155 MB 3B tensor. Some Firefox adapters expose only nine storage buffers. Unsupported options are disabled before a download. Preflight requests and releases a real graphics device, inspects exposed features/limits, WebAssembly vector support, isolation, and concurrency. Memory is only an optional coarse hint; free memory, exact processor model, and available graphics memory cannot be reliably inferred. No model or inference vendor is fetched by preflight. Automatic selection is a conservative heuristic: compatible cached formats first, otherwise ONNX graphics in Firefox, WebLLM graphics in other browsers, then the remaining compatible graphics engines and processor. It does not guarantee the globally fastest engine. Explicit Processor never selects graphics. A same-format wllama graphics initialization failure can retry processor mode without downloading again. Cancellation, invalid input, and exhausted deadlines never trigger that retry. A graphics failure during generation ends the attempt, unloads it, and reprobes before offering a new load action; partial output is never replayed. Switching from a failed graphics engine to another model representation requires a new explicit download action. No automatic larger models, background benchmark downloads, or server inference.

Each load validates inference with a non-student warm-up (60-second deadline). The warm-up verifies readiness; it is not used to rank generation speed. The optional comparison generates a fixed Python function instead of timing a one-word reply. Session-only measurements include the artifact revision, engine version, execution profile, thread count, context budget, and fixed workload. Only identical completed outputs are compared. Automatic offers a two-minute comparison when multiple compatible profiles already have their model format cached; it loads one at a time, requests no additional weights, and uses total request latency rather than unequal token rates. Unmeasured engines remain unknown. Measurements do not persist or create a hardware fingerprint.

Firefox processor inference avoids the slower Asyncify compatibility build when Memory64 is available. Firefox wllama graphics requires both native JSPI and Memory64; the known-slow compatibility graphics path is excluded. WebLLM remains an independent graphics option when the required limits are available. For fresh downloads, Automatic prefers ONNX graphics in Firefox when its limits are met. Existing compatible downloads remain preferred to avoid a silent second-format download. For an already cached GGUF, Automatic initially chooses processor mode; the student can explicitly select ONNX for graphics or compare compatible cached engines. The ONNX backend does not require JSPI or Memory64.

A working integrated Intel graphics device can use graphics acceleration; a dedicated graphics card is not required. Processor mode remains available when browser graphics support is missing. The current classroom target is 16 GB. The original 8 GB baseline still requires physical-device validation, including an Intel laptop with integrated graphics, its real browser/driver combination, other tabs, and sustained generation. A development-machine smoke test cannot establish that acceptance criterion.

## Download, storage, deletion

Download is explicit. A tiny cache write/read is checked before any uncached model transfer. When the browser exposes a storage quota, known-insufficient space is rejected before requesting model data; the estimate cannot guarantee that a later write will succeed. Acquisition uses an abortable stream in the owning page, and releases the cross-tab lock only after the stream settles. It streams actual byte counts one file at a time with a labeled progress element. Model HTTP requests use `cache: no-store`; reusable files live only in dedicated Cache API stores: `sebook-llm-gguf-v1`, `sebook-llm-onnx-v1`, `webllm/model`, `webllm/config`. The GGUF and ONNX weight files are requested in validated 32 MiB byte ranges, stored as separate entries, and reconstructed as file-backed composite Blobs. The ONNX adapter serves those files through a read-only custom cache with remote model loading disabled; it creates no Transformers.js cache. ONNX Runtime needs a contiguous in-memory model buffer at initialization, unlike wllama’s Blob loader, so peak memory remains an additional acceptance check on physical 8 GB machines. This bounds individual cache entries and supports resuming completed ranges; it does not change the model bytes. Interrupted transfers retain completed entries but never mark incomplete files complete. An engine switch can retain multiple formats until deletion. Browser storage eviction can require a fresh download. Private/denied storage is reported rather than pretending a persistent cache exists.

The page offers Cancel, Unload from memory, and Delete downloaded model. Deletion also lives at `/cookies/#browser-model-storage` and is included in Delete everything. It clears all four stores plus any legacy `webllm/wasm` cache and leaves learner drafts/progress intact. A BroadcastChannel (`sebook-browser-llm-storage`) asks active tabs to terminate model workers; the Web Lock (`sebook-browser-llm-model`) ensures deletion waits for their writer ownership to end. If another tab cannot respond, deletion reports that it must be closed instead of falsely claiming success. Web Locks are required for safe model acquisition/deletion. No additional cookies/localStorage/IndexedDB/preferences are introduced. Specifications and replies are page-memory-only.

Executables are fetched from pinned jsDelivr versions and an immutable GitHub commit, with SHA-256 integrity checks and small license/provenance records. No model weights or large runtime files are stored in the repository. They use ordinary browser HTTP caching and are not model data. Verified executable assets use temporary blob URLs; WebLLM’s model library bypasses its writable model cache. The shared tutorial isolation service worker enables processor threads where supported; it never caches model weights.

## Verification

Fast checks: `node --test scripts/tests/browser-llm*.test.js`.
Browser interaction checks: `npx playwright test tests/tutorial-llm.spec.js --project=chromium` against a fresh Jekyll build.

Real inference and hardware acceptance results are recorded in the implementation report. Orchestration fixtures are not evidence that a model or graphics adapter works. ## Current 3B validation status

The 3B artifacts and runtime library are pinned. Real Chrome WebLLM and Firefox ONNX initialize and generate on the M4/16 GB development device. This establishes runtime operation, not reliable assessment of a student's specification. Several complete Warehouse Rover specifications still produced incorrect implementations in both engines. Three Firefox runs with a 384-token allowance took 35–46 seconds; all missed stated requirements. Increasing the allowance to 768 or simplifying the system prompt did not make the complete Chrome example pass. A generic second-pass model review also failed to correct the program, so it is not included in the student workflow.

A further real Firefox generation completed with the actual GPU device constrained to nine storage buffers and 1 GiB buffer/binding limits: 373 tokens in 58.8 seconds under concurrent browser testing. Its output still missed stated rules. The older ten-buffer WebLLM error is therefore avoided by this ONNX path; this run does not establish a general speed guarantee.

The verified 3B GGUF also initialized and completed real processor inference through wllama in Chrome, using four threads. A cached run of the complete rover contract took 67.0 seconds and still produced an incorrect implementation. Its download and cached reload used the production range/cache path; model files stayed outside the repository.

With complete-file prompting and source inspection, a real Chrome WebLLM generation produced a structurally complete file in 17.5 seconds. In a separate repair trial, the first response was deliberately replaced with the reported missing-helper fixture; the real model's one retry supplied every missing helper in 23.7 seconds. Neither candidate passed the behavioral checks: the first violated rover rules and the repaired candidate had a runtime error. These trials validate the completeness workflow, not semantic correctness or a model success rate.

The whole-program exercise remains an experimental learning aid, not an automatic grade. The source and instructor review remain authoritative, and passing model checks never gates progress. The authored grader is independently checked against the 108-line original, two alternative algorithms, and behavioral mutants. Runtime initialization, generated-program accuracy, and grader accuracy are separate validation results.

Peak runtime RAM has not been measured. Physical Safari and an 8 GB Intel laptop remain unverified. Record engine-specific constrained-device and processor checks separately before making broader acceptance claims.

## Historical 1.5B verification and environment limits

The following measurements used **Qwen2.5-Coder 1.5B Instruct**, before the switch to 3B. The development device is an Apple M4 MacBook Air with 16 GB RAM. That development run exercised real 1.5B inference on Chrome using CPU, wllama graphics, and WebLLM graphics, plus the complete generation/apply/check flow. A temporary WebKit session hit its quota. In this host's persistent Playwright WebKit profile, even four-byte Cache API writes could not be read back (same-origin and cross-origin, with and without isolation). This browser environment therefore cannot establish Safari support. The feature detects that storage failure before model transfer. Physical Safari and the 8 GB Intel classroom baseline remain unverified.

On the M4/16 GB development device, three Chrome WebLLM **1.5B** runs of the complete demonstration (129 input tokens, 47 output tokens, identical output) took 1.29–1.39 seconds with a 128-token prompt batch, approximately 42–46 output tokens/second after the first token. Testing batches of 256 and 512 gave small, noisy differences; the conservative default remains 128. These are local historical measurements, not 3B timings or guarantees for 8 GB classroom devices. Firefox’s nine-storage-buffer limit could not run that pinned WebLLM build: its Qwen prefill shader needed ten storage buffers.

The **1.5B** Firefox graphics prototype used real Playwright Firefox 146 on the M4 Mac, with the actual GPU device explicitly capped at nine storage buffers. Transformers.js 3.8.1 / the JavaScript WebGPU backend completed the same 47-token demonstration in 6.04 seconds, with first text at 1.34 seconds (about 10 tokens/second during decoding). A repeated 34-token fixed function took 4.17 seconds after initial shader compilation. Transformers.js 4.3.2 / the native WebGPU backend failed this constrained-device test because a shader required ten buffers. These measurements supported the backend choice for 1.5B; they do not establish 3B compatibility, performance in every Firefox version, or performance on an 8 GB Intel laptop.

Integrated **1.5B** Firefox verification also covered streamed acquisition, cache-only reload with no model requests, explicit application, Python checks, stale-generation cancellation, and navigation. With those generation settings, the complete tutorial example took 6.3 seconds. On a real device constrained to nine buffers and 512 MiB buffer/binding limits, a 719-token input completed; a 919-token input was rejected in 42 ms before inference by the 768-token guard. Scoped screen/print accessibility audits covered the tutorial, its print page, cookies, settings, and glossary; this was not a whole-site audit.
