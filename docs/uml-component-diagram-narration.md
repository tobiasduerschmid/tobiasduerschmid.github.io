# Component diagrams narration

A narrated lesson at the top of the
[UML Component Diagrams chapter](../SEBook/uml_component_diagram.md) that teaches
students with no UML experience to read and draw component diagrams. It reuses
the design-pattern player (`kind: pattern`) with its own parts, ArchUML
diagrams, and cards, and it has no code panel.

The visual package was generated from readable diagram sources with a small
script; edit the JSON directly, keeping each diagram's `label`, `description`,
and `caption` in step with its source.

## Example and structure

The running example is a seat-alert app: a student sets an alert for a full
class, and at night a poller notices an open seat and the app texts the
student. The instructor chose it on 2026-10-29 over a dorm laundry app (its
washing machines invite mixing hardware nodes with software components) and a
party playlist app (honestly swapping real streaming services needs an adapter,
which adds complexity). The example gives every idea a concrete moment:
500 browser copies of one web folder (run time versus code), a library inside
the poller, a fake registrar for tests (replacement through an interface), a
service with three ports, request–reply, queued, and database connectors, and
an outside text gateway whose failure can be traced along dependencies.

The parts are Components, Interfaces, Connectors, and Reading. The lesson opens
with an ambiguous whiteboard sketch (a problem the notation solves), returns to
it in the mistakes scene, and ends with a transfer task (push notifications)
and a summary quiz on a new app (a campus shuttle tracker). It has four
prediction cues: running copies, swapping the registrar, a 30-second restart,
and the transfer.

The audience has no class- or sequence-diagram experience. The lesson defines
interface, operation, provided, required, port, and connector from scratch, and
mentions class, sequence, and deployment diagrams only as answers to different
questions.

## Where the references differ

- **What a component is.** The attached Rumbaugh, Jacobson, and Booch *UML
  Reference Manual* is the 1999 first edition (UML 1.x). It defines a component
  as a physical unit of implementation and draws it as a rectangle with two
  small rectangles on its side. UML 2.5.1 defines a modular, replaceable part
  that may be logical or physical, manifested by artifacts, and draws it with
  the «component» keyword or a small icon in the corner. The lesson follows
  UML 2.5.1 and keeps what both agree on: well-defined interfaces, dependence on
  interfaces rather than on other components, and replaceability.
- **Run-time framing.** UML 2.5.1 also allows design-time (logical)
  components. The CS 130 lectures and *Views and Beyond* use component diagrams
  for the run-time view, so the lesson says a component diagram is drawn "for
  the system while it runs" and qualifies the library claim with "in the
  run-time view".
- **Types and instances.** *Views and Beyond* recommends showing instances in a
  component-and-connector view. The lecture slides and the chapter use type
  names. The lesson draws one StudentWeb component for all 500 running copies
  and does not introduce instance notation.
- **Required interfaces.** UML 1.x shows a required interface as a dependency
  arrow to another component's lollipop; UML 2.5.1 adds the socket. The lesson
  uses the socket.
- **Connector arrows.** UML connectors are lines, so the port wiring uses plain
  lines labeled with the kind in angle quotes, as *Views and Beyond* advises.
  Ball-and-socket assemblies need no arrowhead.

## Renderer limits and choices

- ArchUML cannot nest components, so the lesson has no white-box view or
  delegation connectors, like the chapter. The instructor agreed to skip them.
- ArchUML attaches balls and sockets to components, not to ports. The ports
  scene says that each port can carry its own interfaces without drawing them.
- `component Name <<external>>` drops the component, and a quoted display name
  loses its stereotype, so UML notes mark the two parts other organizations run.
- Callouts are ArchUML's teaching overlay, not UML. Each cue that names a symbol
  switches to a diagram variant with one callout on it.

## Pronunciation

`2:13` is spoken as "two thirteen", and the component and interface names are
split into words. "Maya opens" picked up an intrusive *r*, so the trace says
"Maya uses StudentWeb". Check new phrases with Kokoro's tokenizer as described
in the `design-pattern-narration` skill.
